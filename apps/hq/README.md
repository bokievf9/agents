# apps/hq: Директор и головы отделов (этапы 1-2: Маркетинг, Продажи)

Один процесс, один контейнер, одна SQLite (`$DATA_DIR/hq.db`). Спека: `../../../docs/architecture-hq.md`, ядро:
`packages/hq/README.md`. Dono и Polly остаются отдельными ботами.

## Как идёт задача
```
владелец пишет Директору            рутина (cron) -> hq.runRoutine
          |  LLM (strict JSON)               |
          v                                  v
   задача отделу (inbox) + wake головы   задача (creator: routine) + wake
                         \                  /
                          heartbeat, 30 с: голова просыпается
   голова: claim -> разбить (worker.plan или LLM-сплит) -> подзадачи исполнителю -> worker.run
        -> LLM-ревью по чек-листу отдела -> одна доработка -> requestApproval (в очередь) или done -> отчёт
   Директор: 10:00 и /approve собирает очередь всех отделов одной серией с номерами (кнопки)
   владелец: Одобрить / Править / Отклонить -> задача done / rejected
```
Голова владельцу в личку не пишет никогда. Отчёты: запись в журнале задачи (идёт в утреннюю сводку 08:00) и, если
настроены группа, тема отдела и бот отдела, сообщение в тему. Директор пишет сам только три вещи: утреннюю сводку,
пачку на одобрение, алерты (в тихие часы алерты ждут сводки).

## Директор (бот `HQ_BOT_TOKEN`, только `OWNER_TELEGRAM_ID`, личный чат)
Любое сообщение разбирается LLM в одно из: задача отделу, вопрос о статусе, изменение правил, «нужен строитель»
(задача `blocked` с пометкой `builder`, отдел `hq`). Ответ модели не команда: отдел, настройка и агент проверяются по
спискам, неизвестное отклоняется. Изменение правил пишется только после кнопки «Применить»: настройки `tz`,
`summary_time`, `approval_time`, `quiet_hours` или новая строка в раздел «Правила владельца» инструкции агента.
Без LLM (нет ключа) Директор отвечает, что не смог разобрать, команды работают.
Команды: `/status`, `/tasks [отдел]`, `/approve`, `/costs`, `/org`, `/pause <отдел>`, `/resume <отдел>`, `/builders`, `/skip`, `/help`.

## Маркетинг (`src/heads/marketing.ts`)
Бот отдела `MARKETING_BOT_TOKEN` необязателен (тишина без него). Рутины создаются при первом старте (дальше правятся
через `hq import` и не перезаписываются): понедельник 09:00 пакет недели (7 клипов, карусель раз в две недели),
ежедневно 09:00 «что публикуем сегодня» (одобренное на сегодня из `cm_ready`). Задачу владельца голова делит LLM
(`pack` / `topic` / `daily` / `none`); без LLM работают только очевидные формулировки. Исполнитель:
`packages/workers/content-maker`. Правка карточки по частям (сценарий, Instagram, TikTok, Shorts) работает через
`ApprovalEditor` головы. Отклонённый материал закрывает задачу; переделку владелец заказывает новой задачей.

## Сопровождение (`src/heads/support.ts`)
Голова `support-head`, исполнители `packages/workers/monitoring` и `packages/workers/finance`. Бот `SUPPORT_BOT_TOKEN`
необязателен (тишина без него; проверки и алерты работают). Отчёты идут в тему `support` из `HQ_TOPICS`.
- Мониторинг каждые 5 минут идёт от собственного крона головы, а не от рутины: рутина создавала бы 288 задач в сутки.
  События дня (тревога, «снова в норме») собираются в одну задачу «Дежурство ДД.ММ», она закрывается на следующий день
  строкой аптайма. Тревога после двух неудач подряд, один раз; «снова в норме» один раз; в тихие часы тревога ждёт
  сводки (путь Директора). Проверки: `MONITOR_URLS` (по умолчанию health firtech.pro, 200 и ok), срок TLS (меньше
  14 дней), OmniRoute (`OMNIROUTE_HEALTH_URL`), диск `DATA_DIR` (больше 85%), контейнеры только при `MONITOR_DOCKER=true`.
- `MONITOR_DOCKER`: нужен том `/var/run/docker.sock` (в `compose.yaml` закомментирован). Доступ к сокету Docker равен root
  на сервере, а `:ro` не ограничивает API: оставляйте выключенным, пока нет реальной нужды.
- Рутины (создаются при первом старте): `support-daily` 07:50 (строка финансов и аптайма в утреннюю сводку) и
  `support-weekly` воскресенье 20:00 (расходы за месяц на данный момент, прогноз). Расходы берутся из `costs` с реальным
  usage модели; цены за 1M токенов в таблице `prices` (`hq.setPrice`), бесплатные модели шлюза стоят 0. Постоянные расходы
  (`FIXED_COSTS_USD_MONTH`) делятся на дни месяца. Лимит отдела: `SUPPORT_BUDGET_USD`.

## Продажи (`src/heads/sales.ts`)
Бот отдела `SALES_BOT_TOKEN` (это @firtech_leads_bot) необязателен: без него отчёты только в журнал и утреннюю сводку. Бот
ничего не слушает, только пишет в тему «sales» группы HQ. Исполнители: `packages/workers/lead-intake` (Приёмщик лидов) и
`packages/workers/prospector` (Разведчик), таблицы `li_*` и `pr_*` в общей SQLite.
- **Лид с сайта.** `POST /lead` (`src/webhook.ts`, порт `WEBHOOK_PORT`, заголовок `x-lead-token` = `LEAD_WEBHOOK_TOKEN`, поля формы
  firtech.pro плюс необязательный `source`) создаёт задачу отдела (`meta.lead`) и будит голову. Без токена сервер не стартует.
  Приёмщик ставит температуру правилами, достаёт нишу и срок (LLM, strict JSON, без LLM эвристики), берёт слот из формы или
  предлагает два ближайших рабочих дня в `SLOT_HOURS`, пишет карточку и черновик первого ответа. Голова проверяет ответ по
  чек-листу (один раз возвращает), ответ уходит одобрением `lead_reply` (старт на `REPLY_LEVEL`, по умолчанию 1: после
  одобрения готовый текст и контакт приходят владельцу, отправляет он сам), вопрос о цене отдельным `lead_price`
  (`locked`, всегда уровень 0, с метками [цена] / [срок] до правки). Горячий лид дополнительно алертом через Директора.
- **Карточки Разведчика.** Рутина `sales-daily-cards` 10:00 (`BATCH_SIZE` новых бизнесов по приоритету ниш) и `sales-followups`
  10:05 (дожимы через 3 и 7 дней после «Отправлено», через 10 дней статус «без ответа»). Каждая карточка это дочерняя задача и
  одно одобрение (`prospect_first/followup/reply`, все `locked`: «Отправлено» только фиксирует, что владелец отправил сам) с
  кнопками «Скопировать» (голый текст отдельным сообщением), «Править», «Пропустить», «Отправлено».
  Чтобы карточки пришли в то же утро, поставьте `approval_time` позже 10:05 (через Директора) или сдвиньте рутину.
- **Ответ бизнеса.** `/reply <id>` или обычная фраза («Cambridge ответили: ...», интент `sales_reply` Директора): статус
  `replied`, дальше владелец пересылает текст ответа, Разведчик готовит черновик с двумя слотами (11:00 и 15:00), цен модель не
  называет. Задачу владельца вроде «покажи воронку Разведчика» голова разбирает LLM (`batch` / `followups` / `stats` / `none`).
- **База Разведчика.** Загрузка CSV: `pnpm --filter hq run import-prospects <csv>` (dev) или в контейнере
  `docker compose exec hq node dist/import-prospects.js /app/data/prospects.csv` (файл положить в `/opt/fir-agents/data/hq`).
  Повторный запуск безопасен (дедуп по «название + город»).
- **Перенос со старых сервисов.** Сервисы `lead-intake` и `prospector`, их образы и CI-задачи удалены. Данные не переносим
  (ценных данных пока нет): на сервере `/opt/fir-agents/data/lead-intake` и `/opt/fir-agents/data/prospector` можно удалить после
  первого запуска нового `hq`; контейнеры старых сервисов `docker compose up -d --remove-orphans` уберёт сам. Telegram-диалог
  с клиентами (публичный бот) не переехал: заявки приходят только с формы сайта. `SALES_BOT_TOKEN` теперь токен бота отдела
  (раньше `TELEGRAM_BOT_TOKEN` у lead-intake, `PROSPECTOR_BOT_TOKEN` у Разведчика), `LEAD_WEBHOOK_TOKEN` и порт те же.
### Остальные исполнители отдела (этап 1, текст, без платных API)
| Исполнитель | Рутина | Что делает | Документ |
|---|---|---|---|
| Трендвотчер | 08:30 ежедневно, вс 20:00 итог недели | 5 хуков и форматов дня из Google Trends и YouTube, отдаёт их Контент-мейкеру | `packages/workers/trend-scout/README.md` |
| Публикатор | 09:00 «что публикуем сегодня» | пакеты публикации по платформам, кнопка «Опубликовано» (ручная публикация) | `packages/workers/publisher/README.md` |
| SEO | пн 11:00 | проверка сайта и llms.txt, до 5 правок в пачку одобрения, `builder` для кода | `packages/workers/seo/README.md` |
| Аналитик | пн 08:00 | отчёт из данных HQ: 5 чисел и 3 рекомендации | `packages/workers/analyst/README.md` |
Задачи трендов, SEO и отчёта голова запускает напрямую (без чек-листа контента); предложения SEO идут в очередь одобрений
(`seo_proposal`, уровень 0). Кнопка `pb:<id>` («Опубликовано») обрабатывается в `src/index.ts` и пишет `published_at`.
Все источники необязательны: без ключа источник выключен.

## Производство (`src/heads/production.ts`)
Голова `production-head`, исполнители `packages/workers/project-manager`, `reviewer`, `deployer` (таблицы `pm_*` и `dp_targets`).
Бот `PRODUCTION_BOT_TOKEN` необязателен (тишина без него), отчёты в тему `production`. Лимит: `PRODUCTION_BUDGET_USD`.
- **Как продажа становится проектом.** `/project <клиент>: <что делаем>` (Директор: команда или обычная фраза) либо сигнал Продаж
  «КП одобрено/оплачено» (`ProductionHead.createProjectTask({client, what, product?, source: 'sales'})`, задача отдела с
  `meta.action = project`). Проектный менеджер создаёт проект и этапы по типу работы (сайт, бот, приложение, автоматизация):
  бриф, прототип, сдача, оплата с целевыми датами. Короткое ТЗ (LLM пишет текст, шаблон на случай отказа; цену и срок модель
  не называет, остаются `[цена]` и `[срок]`) уходит на одобрение владельцу, уровень 0 и `locked`.
- **Как идут builder-задачи.** Одобрено ТЗ: проект становится `active`, этапы «Прототип» и «Сдача» превращаются в задачи
  (`blocked` + тег `builder`, `meta.kind = work`), мост создаёт GitHub issues для Claude Code. Закрытый issue возвращает задачу
  голове с `meta.result`. Ссылка на ветку или PR: создаётся задача «Ревью: ...» (`meta.kind = review`, `labelHint = review`,
  чек-лист: безопасность, тесты, секреты, миграции, модель Opus), этап ждёт её закрытия. Нет ссылки: ревью не запрашивается, этап
  закрывается с пометкой. Закрыт этап «Сдача»: задача «Деплой: ...» (чек-лист: CI, окружение, DNS, TLS, health, откат) и задача
  отделу `support` «добавить <url> в мониторинг». Цель деплоя: `/target <проект> ours|client <путь или хост> [url]`
  (пароли и токены не принимаются). Последний закрытый этап закрывает проект и напоминает про `/lesson` и акт.
- Просрочки: рутина `production-overdue` 10:30 считает открытые этапы активных проектов за датой; строка идёт в утреннюю сводку.
- Статус клиенту: `/pstatus <проект>`, текст по фактам этапов без цен, уровень 1: приходит владельцу, отправляет он сам.
  Этап вручную (бриф, оплата): `/mdone <проект> brief|prototype|delivery|payment`.
- Команды работают через Директора: `/project`, `/pstatus`, `/target`, `/mdone`, а свободная фраза разбирается в интент
  `production_command` (команда проверяется по списку зарегистрированных).

## Бэк-офис (`src/heads/backoffice.ts`)
Голова `backoffice-head`, исполнители `packages/workers/documents` и `knowledge` (таблицы `bo_documents`, `kb_lessons`). Бот
`BACKOFFICE_BOT_TOKEN` необязателен, лимит `BACKOFFICE_BUDGET_USD`. Финансы остаются в Сопровождении.
- `/doc <договор|оферта|политика|акт> <клиент>`: шаблон из `packages/workers/documents/templates/*.md` заполняется данными проекта
  (`pm_projects`, этапы) и клиента, без LLM. Что неизвестно, остаётся `[заполнить: ...]`, цена и срок остаются `[цена]` и
  `[срок]`. Документ идёт на одобрение (`bo_document`, уровень 0, `locked`), версии в `bo_documents`. Утвердить текст с
  неснятыми метками нельзя: владелец правит текст кнопкой «Править». Утверждённый текст приходит владельцу, клиенту отправляет он.
  Шаблоны юридически не проверены, перед боевым использованием их смотрит юрист.
- База знаний: файлы в репозитории `knowledge/` (`playbooks/`, `lessons/`). `/lesson <проект>: <урок>` пишет в `kb_lessons`;
  рутина `backoffice-lessons-weekly` (воскресенье 19:00) превращает неотправленные уроки в builder-задачу «Обновить
  knowledge/lessons», строитель коммитит их. `/kb <запрос>` ищет по урокам и заголовкам плейбуков (`KNOWLEDGE_DIR`, в образе
  `/app/knowledge`).
- Строка утренней сводки: документы, ждущие решения.

## Мост к строителям (`src/bridge.ts`)
Задача `blocked` с тегом `builder` без `meta.issue` (Директор по «нужен строитель», голова маркетинга для SEO-правок и клипов)
становится issue в `GITHUB_REPO` (по умолчанию `bokievf9/agents`) с меткой `builder`. Заголовок: название задачи. Тело: отдел,
id задачи HQ, контекст (описание, последние комментарии, для клипа одобренный сценарий, субтитры, CTA, подписи платформ и
целевая спецификация 9:16, 20-40 с, mp4 h264, субтитры вшиты, синтез русского голоса), чек-лист приёмки и последняя
строка `HQ-TASK: <id>`. `meta.issue = {number, url}`, в журнал пишется событие `builder_issue_created`.
- **Без `GITHUB_TOKEN`** мост выключен: ничего не создаётся и не опрашивается, задача остаётся `blocked` и видна в утренней
  сводке и в `/builders`. Токен fine-grained, только Issues read/write на один репо.
- **Опрос** каждые `BUILDER_POLL_MINUTES` (10) минут: issue закрыт, значит задача уходит в `review` к голове отдела,
  последний комментарий пишется событием «Результат строителя», путь под `/opt/fir-agents/data/hq/artifacts/` или URL из него
  кладётся в `meta.result`. Issue открыт снова: задача возвращается в `blocked`. Метка `builder-blocked-question` на issue:
  один алерт владельцу (путь Директора) и событие с текстом вопроса.
- **Клипы.** Одобренный сценарий клипа: голова маркетинга создаёт дочернюю задачу «Собрать клип: <название>» (`blocked`, `builder`,
  `meta.action=build_clip`, `meta.itemId`, сценарий, субтитры, CTA, подписи, спецификация). Когда она в `review` с `meta.result`,
  пачка публикации этого материала показывает «Файл: <путь>».
- **Директор:** `/builders` (открытые задачи строителям со ссылками на issue), в утренней сводке счётчик открытых issue.

### Как строитель закрывает issue
1. Положить результат в `/opt/fir-agents/data/hq/artifacts/` (файл) или выложить по URL.
2. Последний комментарий перед закрытием: результат одной-двумя строками, в нём путь или URL (берётся первый).
3. Строка `HQ-TASK: <id>` в теле issue не удаляется и не меняется.
4. Закрывать issue только после этого комментария: после закрытия мост читает именно последний комментарий.
5. Вопрос к владельцу: комментарий с вопросом и метка `builder-blocked-question`, issue не закрывать. Переоткрытие вернёт задачу в `blocked`.

## Инструкции агентов
`instructions/director.md`, `instructions/marketing-head.md` и `instructions/sales-head.md` (русский) загружаются в таблицу `agents` один раз при первом
старте (`ensureAgent`). Дальше правда в базе: меняются через Директора (кнопка) или `hq import`. Чек-лист проверки
материалов лежит в инструкции головы маркетинга.

id отдела), `DATA_DIR`, `CLIPS_PER_WEEK`, `CAROUSELS_PER_WEEK`, `MARKETING_BUDGET_USD`, `TRUST_THRESHOLD`.

## Как добавить отдел
1. Исполнители: `packages/workers/<имя>` (контракт в `packages/hq/README.md`).
2. Инструкция головы `apps/hq/instructions/<отдел>-head.md` с чек-листом отдела; агенты и рутины в `src/org.ts` (`ensureAgent`,
   `scheduleRoutine`; бот: имя переменной в поле `bot`).
3. Голова: `src/heads/<отдел>.ts` по образцу `marketing.ts` (`onHeartbeat`, разбиение, `worker.run`, ревью, `hq.requestApproval`,
   отчёт через `Reporter`). Тип одобрения регистрирует голова (`hq.registerKind`).
4. `src/index.ts`: создать голову, добавить в `HeartbeatWorker` (по `agent.id`), при боте отдела добавить отправителя в `senders`.
5. Тесты по образцу `tests/marketing.test.ts` (`MemoryMessenger`, `MockLlm`, `:memory:`).

## Запуск
`pnpm --filter hq dev` (`.env.local`). Docker: `apps/hq/Dockerfile`, сервис `hq` в `compose.yaml` (единственный порт `127.0.0.1:8787` для webhook лидов, `read_only`,
данные `/opt/fir-agents/data/hq`), образ `agents-hq` в CI. Экспорт оргструктуры:
`docker compose exec hq node node_modules/@fir/hq/dist/cli.js export`.

## 1. Что приложение делает для клиента (3 сценария)

Условия контракта AI-native сохраняются: единица результата «обработанная заявка = ответ клиенту и запись в CRM»,
передача человеку как фича, агент «берёт рутину, решения за людьми».

1. **Первый ответ и квалификация в Открытой линии.** Клиент Битрикс24 подключает наш коннектор к Открытой линии
   (сайт-чат, Telegram, WhatsApp, Instagram у него уже подключены к линии Битрикса). Агент отвечает за минуту,
   круглосуточно, по базе знаний клиента, собирает имя, телефон, задачу. Итог: лид в CRM с карточкой диалога.
2. **Запись лида и сделки.** Из диалога агент создаёт лид (`crm.lead.add`: имя, телефон, `SOURCE_ID`, `COMMENTS` с
   резюме), привязывает к ответственному по правилу клиента; для существующего контакта пишет комментарий в таймлайн
   вместо дубля. Сделку создаёт человек (решение за людьми), агент только предлагает.
3. **Передача человеку.** Агент передаёт диалог сотруднику или очереди (`imopenlines.bot.session.operator` или
   `.transfer`) с кратким резюме в чате; порог передачи клиент задаёт сам (слова-триггеры, «злой клиент», вопрос вне базы,
   сумма выше порога). Агент не берёт цену, срок и договор на себя: подставляет `[цена]`, как везде в HQ.

Что не делаем в версии 1: исходящие рассылки, обзвон, правка сделок, работу с задачами и календарём, свой
чат-интерфейс внутри Битрикс24 кроме страницы настроек.

## 2. Архитектура поверх HQ

### 2.1 Что уже есть в HQ и на что опираемся
- `apps/hq/src/webhook.ts` держит один HTTP-сервер на `WEBHOOK_PORT` (127.0.0.1:8787, nginx снаружи). Маршруты:
  `/lead`, `/audit` (`LEAD_WEBHOOK_TOKEN`), `/chat` (`WEB_CHAT_TOKEN`), `/admin/*` (`ADMIN_TOKEN`, кабинет с
  `CABINET_TOKEN` и белым списком `cabinetRouteAllowed`), `/agent/<publicId>/chat` (публичный маршрут живого агента
  клиента с CORS), `/events`, `/pay`, `/media`. Правило из `docs/public-api.md`: токены не подменяют друг друга,
  без токена маршрут отвечает 404. Битрикс24 не умеет слать наши заголовки, поэтому для его маршрутов проверка
  своя: `application_token` (см. 2.4), а не `x-*-token`.
- Агент клиента уже есть: `Playground` (`apps/hq/src/playground.ts`): персона из ниши и знаний, инструменты
  `faq_search`, `booking_slots`, `book_slot`, `capture_lead`, `handoff_human`, лимит `msgsPerDay`, состояния
  `draft|live`, журнал `pg_conversations`, 90 дней хранения, `chat()` с каналами `cabinet|widget|demo|telegram`.
  Telegram уже подключён по тому же образцу (`tg-runner.ts`, `chatTelegram`). Битрикс24 становится ещё одним каналом:
  `chatBitrix24(agentId, portalChatId, text)` с каналом `bitrix24`.
- Токены клиента хранятся шифрованием AES-256-GCM под `PG_SECRET` (`Playground.encrypt/decrypt`): тот же приём для
  токенов Битрикс24. Без секрета токен не принимается (как у Telegram).
- Кабинет: `cabinet-api.ts` (`/admin/clients/:id/agents/...`), тред агента `agent-<id>`, передача человеку P-21
  (строка клиенту в тред агента и письмо). `chats.ts` склеивает диалоги по клиенту; сообщения Битрикс24 сюда не
  попадают текстом, только маска и счётчики (правило логов: никаких текстов и контактов клиентов).
- Одобрения (`ApprovalQueue`): первый ответ уровня 1 допустим для FAQ, всё с ценой уровня 0.

### 2.2 Новый модуль `apps/hq/src/bitrix24.ts`
Фабрика `createBitrix24({ db, playground, secret, siteUrl, clientId, clientSecret, now })`, подключается в
`apps/hq/src/index.ts` рядом с агентом (включается `B24_CLIENT_ID` + `B24_CLIENT_SECRET`, без них маршруты 404, одна
строка в `missingTokens`, как остальные). Маршруты в `webhook.ts` (префикс `/b24/`, публичные, без нашего токена):

| Маршрут | Кто зовёт | Что делает |
|---|---|---|
| `POST /b24/install` | Битрикс24 при установке (поле «Application installer URL») | Принимает `auth` (`access_token`, `refresh_token`, `member_id`, `application_token`, `client_endpoint`, домен), сохраняет портал, создаёт агента, регистрирует коннектор и бота, отвечает 200; затем редирект на страницу настроек |
| `GET/POST /b24/app` | Фрейм приложения («Application URL», `placement`) | Страница настроек во фрейме: знания, порог передачи, выбор Открытой линии, статус; в конце установки зовёт `BX24.installFinish()` |
| `POST /b24/events` | Битрикс24 (обработчик событий) | `ONIMBOTV2MESSAGEADD`, `OnImConnectorMessageAdd`, `ONAPPUNINSTALL`, `ONAPPPAYMENT`; проверка `application_token`, ответ 200 быстро, обработка в очереди |
| `POST /b24/uninstall` | Битрикс24 | Удалить токены и данные портала, остановить агента |
| `GET /b24/health` | наши проверки | `{ok}` |

Страница настроек не делает отдельного клиентского аккаунта: внутри Битрикс24 пользователь уже авторизован,
но управление агентом остаётся в нашем кабинете (ссылка «Открыть кабинет Fir Tech»). Во фрейме минимум:
выбор линии, порог передачи, пауза агента, статус и счётчик обработанных заявок.

### 2.3 Хранение: таблицы в SQLite HQ (`migrate`, префикс `b24_`)
- `b24_portals`: `member_id` (ключ), `domain`, `client_endpoint`, `access_token_enc`, `refresh_token_enc`,
  `expires_at`, `application_token_enc`, `scope`, `agent_id`, `client_id` (кабинетный клиент, если связан), `lines`
  (JSON: id линии, код коннектора, id бота), `state`, `installed_at`, `paused`.
- `b24_chats`: `member_id`, `chat_id`, `agent_conv`, `lead_id` (id лида в Битрикс24), `status` (`bot|human|closed`),
  `last_at`. Без текстов; текст живёт только в `pg_conversations` по правилам площадки.
- `b24_events`: идемпотентность (`event_handler_id` + `message id`, окно 24 часа): доставка повторов не
  гарантирована ни в одну сторону.
- Журнал и счётчики по правилам HQ: только id и числа.

### 2.4 Авторизация и обновление токенов (по документации)
- Установка отдаёт OAuth 2.0 токены: `access_token` живёт 1 час, `refresh_token` 180 дней; код авторизации живёт
  30 секунд. Вызовы REST идут на `client_endpoint` портала с `auth=<access_token>` (или заголовком).
- **Обновление**: `GET https://oauth.bitrix.info/oauth/token/` с `grant_type=refresh_token`, `client_id`,
  `client_secret`, `refresh_token`. Новый `refresh_token` заменяет старый (ротация), поэтому запись в БД идёт в одной
  транзакции, а параллельные обновления одного портала сериализуются блокировкой на `member_id`. Обновляем только
  по ответу `401 expired_token` и повторяем вызов; по расписанию не обновляем. Страховка: раз в 60 дней холостой
  вызов `app.info` по каждому порталу, чтобы 180-дневное окно не истекло. Ошибка `PAYMENT_REQUIRED` значит «срок
  оплаты вышел или приложение удалено»: портал в состояние `suspended`, агент молчит, владельцу строка в инбокс.
- Проверка входящих событий: `application_token` сохраняется при установке (по `member_id`), любое событие с другим
  значением получает 403. Для бота v2 верхний `auth.application_token` сверяется отдельно от `data.bot.auth`.
  `member_id` в событии должен совпасть с известным порталом, иначе 404.
- `client_secret` Битрикс24 живёт только в env HQ (`B24_CLIENT_SECRET`), не в браузере и не в логах.

### 2.5 Поток сообщений
Выбор канала (открытый вопрос 5.1): **рекомендация: бот Chatbots 2.0 на Открытой линии**, коннектор `imconnector` не
нужен, пока у клиента каналы уже подключены к линии Битрикса.
1. Клиент пишет в любой канал линии. Битрикс24 шлёт `ONIMBOTV2MESSAGEADD` на `/b24/events` (формат
   `application/x-www-form-urlencoded`, ключи вида `data[chat][entityType]`, значения строками; обрабатываем только
   `LINES`).
2. HQ ищет агента портала, зовёт `chatBitrix24`, получает ответ (санитайзер без цен и дат остаётся), отвечает через
   `imopenlines.bot.session.message.send`. Для `capture_lead` зовёт `crm.lead.add`; найденный контакт обновляет
   через `crm.contact.*`, а не плодит дубли (проверить `crm.duplicate.findbycomm`).
3. `handoff_human`: `imopenlines.bot.session.operator` (первый свободный) или `.transfer` на очередь/сотрудника из
   настроек; перед этим в чат уходит резюме. Бот может остаться (`LEAVE=N`) или выйти (`LEAVE=Y`), по настройке.
4. Лимиты: общий лимит REST на портал по утечке ведра (тариф Enterprise 5 запросов/с, порог 250; остальные 2/с,
   порог 50), `batch` до 50 вызовов, при `503 QUERY_LIMIT_EXCEEDED` повтор с растущей паузой, при `429
   OPERATION_TIME_LIMIT` пауза до `operating_reset_at`. Один запрос REST живёт не дольше 60 с. Ответ на событие
   отдаём 200 за секунды, остальное делаем в очереди.
Запасной путь, если Открытая линия не подходит: свой коннектор (`imconnector.register`, `activate`,
`connector.data.set`, `send.messages`, события `OnImConnectorMessageAdd`, `send.status.delivery`); методы
`imconnector.*` работают только в контексте приложения, вебхуком их не вызвать.

### 2.6 Данные и безопасность
- Данные портала лежат на нашем сервере в Сингапуре (контракт AI-native). **Риск для КЗ**: закон Казахстана о
  персональных данных требует хранить базы персональных данных граждан РК на серверах в Казахстане (из общих знаний,
  в этой сессии не проверено; нужна консультация юриста). Для решения владельца: либо пометить это в политике и
  оговорить в оферте, либо держать для КЗ-порталов хранение диалогов минимальным (маска и счётчики, как у нас уже
  заведено для анонимных чатов).
- Права приложения (scope) минимальные: `imbot`, `imopenlines`, `crm`, `user` (чтение списка сотрудников для
  передачи), при необходимости `placement`. Чем меньше scope, тем быстрее модерация и выше доверие.
- Удаление: событие `ONAPPUNINSTALL` и маршрут `/b24/uninstall` стирают токены и данные портала; модерация
  просит проверить, что после удаления авторизационные данные уходят из баз.
- Логи запросов и ответов REST хранить не менее 3 дней (требование Маркета), но без текстов клиентов: только
  метод, статус, время, `member_id`.

6. **Два тестовых портала Битрикс24** (модерация проверяет минимум на двух чистых порталах, не на разработческом;

7. **Домен и nginx**: поддомен вида `b24.firtech.pro` с DV-сертификатом (требование: валидный SSL, минимум DV) и

8. **Отправить на модерацию** кнопкой «Submit For Moderation» после проверки карточки; общаться с модератором в чате

## 4. Деньги, сроки и риски

### 4.1 Стоимость и модерация (что подтверждено, что нет)
- **Плата за публикацию и комиссия не найдены.** В FAQ и условиях продаж стоимость публикации не названа; страница
  условий продаж: Битрикс24 сейчас не берёт комиссию с платежей, которые разработчик получает за дополнительную
  функциональность напрямую. Это текущее условие, оно может измениться; зафиксировать при подписании соглашения.
- **Модель размещения**: только два типа: бесплатное решение и бесплатное с платными дополнениями вне Маркета
  (вариант «Users have to pay for external service»). Платная подписка в Маркете описана как внутренние покупки в
  USD или EUR. Для нас это совпадает с USD-политикой. Но: «бесплатное решение должно давать полный функционал без
  срока, без включения и выключения по оплате», а у нас пилот и этапы платные. Значит приложение честно описывается как
  «клиент платит Fir Tech за сервис вне Маркета», в описании обязательно указать внешнюю оплату, лимиты и цены.
  Будет ли модератор принимать «пустое» приложение, работающее только после договора, надо спросить (5.4).
- **Модерация**: обычно 1 до 3 рабочих дней; после отказа повторная подача уходит в конец очереди; модерация может
  быть автоматической и ошибаться (можно запросить ручную); публикацию могут отклонить без объяснения и позже снять.
  После публикации код менять нельзя: каждая версия снова проходит модерацию, пользователи видят прежнюю версию,
  пока новая не принята.
- **Требования, из-за которых возвращают**: пустая страница после установки (приложение обязано автоматически
  открыть свой интерфейс), битые ссылки, непонятное описание установки, не совпадающее с названием EULA, скриншоты не на
  английском интерфейсе, не работающая переустановка, ограничения не описаны. Чат-бот обязан поздороваться при
  приглашении в чат, показать список команд и иметь свою аватарку; название поддерживающего чата должно
  показывать, что это поддержка решения.
- **Для клиента** (оценить, не подтверждено): установка платных/маркетовых решений может требовать подписки
  «Маркет Плюс» на тарифе клиента; на российской странице помощи есть акция 50 % на подписку до 2026-12-31. Что
  требуется для бесплатных приложений в КЗ-портале, проверить (5.5), иначе есть риск «нашёл в Маркете, поставить не
  может».
- Прямой путь без Маркета: **локальное приложение** (создаётся клиентом в «Ресурсах разработчика», модерации нет) и
  **частная публикация** по ссылке. Для первых 3 до 5 клиентов КЗ рекомендуем его: быстрее и не ждёт модерации.

### 4.3 Риски
1. Модерация отклоняет модель «платите нам вне Маркета» (5.4). Смягчение: локальное приложение, вопрос модератору до
   сборки.
2. Хранение данных граждан КЗ за границей (2.6). Смягчение: юрист, минимизация хранения.
3. Лимиты REST у клиента на младших тарифах (2 запроса/с общий лимит портала, делим с остальными приложениями):
   очередь и `batch`, не более N диалогов параллельно.
4. Потеря связи с порталом: `refresh_token` 180 дней с ротацией; потерянный токен или гонка двух обновлений ломает
   портал. Смягчение: блокировка, транзакция, страховочный вызов, алерт.
5. Зависимость от одного дешёвого VPS: падение HQ означает молчащего агента в линии клиента. Смягчение: недельный
   отчёт и алерт простоя (работа H1) должны покрывать портал; при простое бот оставляет линию оператору.
6. Изменения API: версия 1 `imbot.*` устарела, строим только на `imbot.v2.*`; формат событий веб-хука
   `application/x-www-form-urlencoded`, значения строками.
7. Для КЗ и для описания в Маркете обязательны английские тексты и международные контакты; скриншоты только на
   английском интерфейсе портала.

## 5. Открытые вопросы
1. **Бот на линии или коннектор?** Рекомендация: бот v2 (проще, использует уже подключённые клиентом каналы). Нужен
   тест на реальной линии: документация не описывает явно, приходят ли события `ONIMBOTV2*` для чатов линии без
   `isSupportOpenline: true` (с флагом приходят).
2. **Региональная публикация для КЗ**: в документации найден регион «Global» (зоны .com, .de); есть ли отдельный
   регион для .kz и отдельный маркет, не выяснено. Спросить модератора.
3. **Какое юрлицо вендора** (Fir Tech не имеет юрлица в КЗ, у владельца есть решение по структуре компании?) и
   нужен ли лицензионный договор с 1С-Битрикс для публикации.
4. **Подойдёт ли «бесплатное приложение + внешняя оплата»** при нашем правиле «бесплатных триалов нет» и платном пилоте;
   как модерация воспримет приложение, которое без договора отвечает только демо-режимом.
5. **Нужна ли клиенту подписка Маркет Плюс**, чтобы поставить наше бесплатное приложение на портале КЗ.
6. Список поддерживаемых тарифов Битрикс24 (Открытые линии доступны не на всех), записать в описание как ограничение.
7. Цена для клиента Битрикс24: отдельная смета с единицей «обработанная заявка» или та же линейка ИИ-сотрудников
   (решение владельца: деньги и юридическое).
8. Язык интерфейса страницы настроек: RU и EN обязательны (английский для карточки), казахский отложить.

# Публичные точки HQ для сайта: /audit, /status и демо-салон (2026-11-19)

HQ слушает `WEBHOOK_PORT` (compose публикует его только на 127.0.0.1, firtech.pro ходит с того же сервера).
Токен `/audit` тот же, что у `/lead`: заголовок `x-lead-token` (env `LEAD_WEBHOOK_TOKEN`). Все ответы JSON.
Серверы `/audit` и `/status` поднимаются вместе с остальным webhook (нужен хотя бы один из токенов `LEAD_WEBHOOK_TOKEN`,
`WEB_CHAT_TOKEN`, `ADMIN_TOKEN`); без `LEAD_WEBHOOK_TOKEN` маршрут `/audit` отвечает 404.

## Демо-салон в @firtech_bot
Глубокая ссылка: **`https://t.me/firtech_bot?start=demo_salon`** (то же делает команда `/demo` и кнопка «🧪 Попробовать демо» в
приветствии бота). Бот переводит этот чат в песочницу бота-администратора для вымышленного «Салона Лайм»: услуга -> мастер ->
день -> время -> подтверждение -> демо-напоминание через 60 с -> «Перенести / Отменить / Оставить отзыв» -> «Хочу такого бота
себе» (обычная анкета, лид с `source: demo_salon`). Каждое сообщение помечено «Демо, записи не настоящие». Состояние в таблице
`cb_demo`, стирается `/start` или через 24 ч; лиды, задачи и одобрения демо само не создаёт.
В веб-чате (`POST /chat`): сообщение ровно `demo` (любой регистр) или поле `mode: "demo"` в теле возвращает короткое описание
и эту ссылку (`state: "chat"`, без песочницы).

## POST /audit
Бесплатный аудит сайта за 24 часа.
```
POST /audit
x-lead-token: <LEAD_WEBHOOK_TOKEN>
{ "url": "https://example.com", "contact": "@username" | "+998901234567", "name": "Дильноза", "locale": "ru" | "en", "ref": "hero" }
```
- `url`: http(s), до 200 символов, имя хоста с точкой; IP-адреса, `localhost`, `*.local` и т. п. отклоняются (400).
- `contact`: Telegram `@username` (3..32 после `@`) или телефон (7..15 цифр), 3..64 символа.
- `name` (до 80), `ref` (`[A-Za-z0-9_:.-]{1,40}`) необязательны. `locale` обязателен.
- Ответы: `200 { ok: true }`; повтор того же контакта в течение 24 ч `200 { ok: true, duplicate: true }`;
  `400 { ok:false, error:"invalid" }`; `401 unauthorized`; `413 too_large`; `429 rate_limited` (больше 20 аудитов в час на всех;
  лимит по контакту хранится в БД, лимит в час в памяти).
- Что происходит дальше: строка в `mk_audits` и задача Маркетинга `action: audit` «Аудит: <хост>». Голова запускает проверки SEO-исполнителя
  (title, description, h1, canonical, Open Graph, скорость ответа, viewport, кнопка Telegram/WhatsApp, форма, ссылка на Instagram),
  страницу берёт только по публичным адресам (проверка DNS на каждом редиректе, 8 с, 1 МБ). LLM получает только факты (булевы и числа)
  и возвращает ровно 5 находок (проблема и одно исправление) и закрывающую строку с названием продукта, без цен; ответ проходит
  схему, очистку от HTML и ссылок, проверку на цены, иначе берётся шаблон. Недоступный сайт даёт находки про это и просьбу прислать
  Instagram. Результат уходит владельцу как одобрение `audit` (уровень 0, `locked`). После «Одобрить»: если контакт `@username`
  уже писал в @firtech_bot (или аудит заказан командой бота), текст отправляет клиентский бот; иначе владельцу приходит
  простой текст целиком с пометкой «отправьте вручную». Статусы `mk_audits.status`: `queued`, `proposed`, `delivered`, `handed_off`, `rejected`, `failed`.
- В боте: `/audit <сайт>` проходит тот же путь (контакт: `@username` чата, без него `tg:<chatId>`).

## GET /status
Без токена, ответ кэшируется на 60 с (`cache-control: public, max-age=60`), не больше 30 запросов в минуту с одного IP (иначе 429).
```json
{
  "ok": true,
  "generatedAt": "2026-11-19T12:00:00.000Z",
  "services": [
    { "id": "site", "title": "Website", "state": "up" },
    { "id": "omniroute", "title": "AI gateway", "state": "down", "since": "2026-11-19T11:40:00.000Z", "note": "The health check is failing" }
  ],
  "incidents": [ { "startedAt": "…", "endedAt": "…", "service": "site", "title": "Website: health check failed" } ],
  "uptime30d": { "site": 99.9, "omniroute": 100 }
}
```
- `services`: всегда шесть записей `site`, `hq`, `bot`, `omniroute`, `polly`, `dono`; `state` `up | degraded | down | unknown`;
  `since` и `note` только у `degraded` и `down` (фиксированные английские фразы). `incidents`: за 30 дней, не больше 20, новые первыми;
  без `endedAt` значит ещё идёт. `uptime30d`: только для сервисов с данными (процент 0..100, одна цифра после запятой).
- Источник: таблицы `mon_*` мониторинга (`mon_state`, `mon_samples`, `mon_incidents`). `site` = проверки хоста firtech.pro
  (health URL: `down`; сертификат: `degraded`), `omniroute` = проверка `omniroute`, `hq` = проверки `disk` и `docker` (`degraded`),
  плюс сам факт ответа HQ: `up`, а если проверки не запускались больше 30 минут, `degraded`. **`bot`, `polly`, `dono` всегда
  `unknown`**: мониторинг их отдельно не проверяет (Docker-проверка общая). Нет данных мониторинга вообще: `site` и `omniroute` `unknown`.
- В ответ никогда не попадают URL, порты, токены, id проверок и тексты ошибок. Оговорка: образцы `mon_samples` хранятся 7 дней
  (`prune`), поэтому `uptime30d` считается по доступным образцам, а не за полные 30 дней; инциденты хранятся 30 дней.

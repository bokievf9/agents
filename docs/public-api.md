# Публичные точки HQ для сайта: /chat, /audit, /status, /blog, /pay и демо-салон (2026-11-19, чат 2026-11-22)

HQ слушает `WEBHOOK_PORT` (compose публикует его только на 127.0.0.1, firtech.pro ходит с того же сервера).
Токен `/audit` тот же, что у `/lead`: заголовок `x-lead-token` (env `LEAD_WEBHOOK_TOKEN`). Все ответы JSON.
Серверы `/audit` и `/status` поднимаются вместе с остальным webhook (нужен хотя бы один из токенов `LEAD_WEBHOOK_TOKEN`,
`WEB_CHAT_TOKEN`, `ADMIN_TOKEN`); без `LEAD_WEBHOOK_TOKEN` маршрут `/audit` отвечает 404.

**Токены обязательны и не подменяют друг друга** (аудит 2026-11-19): `/chat` работает только с `WEB_CHAT_TOKEN`, `/admin/*` только с `ADMIN_TOKEN`,
`/lead` и `/audit` с `LEAD_WEBHOOK_TOKEN`. Нет токена: маршрут отвечает 404, HQ при старте пишет одно предупреждение.

**IP посетителя.** Сайт передаёт его заголовком `x-visitor-ip` в `/chat`, `/audit` и `/lead`. HQ верит заголовку только если запрос пришёл
с loopback или с адреса из `TRUSTED_PROXY_IP` (по умолчанию шлюз docker-сети контейнера HQ, вычисляется при старте; не вся подсеть) и токен маршрута верный; иначе берётся адрес сокета. Для маршрутов без токена (`/media`, `/agent`, `/pay`, `/status`, `/blog`) от того же доверенного адреса берётся `x-real-ip` (nginx обязан его перезаписывать `$remote_addr`); для `/pay`, `/status`, `/blog` сайт может прислать `x-visitor-ip` вместе со своим токеном. По этому IP считаются лимиты
(чат 60 сообщений в час, аудит 10 в час, лид 20 в час); `x-forwarded-for` не читается.

## Демо-салон в @firtech_bot
Глубокая ссылка: **`https://t.me/firtech_bot?start=demo_salon`** (то же делает команда `/demo` и кнопка «🧪 Попробовать демо» в
приветствии бота). Бот переводит этот чат в песочницу «ИИ-администратора» для вымышленного «Салона Лайм»: услуга -> мастер ->
день -> время -> подтверждение -> демо-напоминание через 60 с -> «Перенести / Отменить / Оставить отзыв» -> «Хочу такого бота
себе» (обычная анкета, лид с `source: demo_salon`). Каждое сообщение помечено «Демо, записи не настоящие». Состояние в таблице
`cb_demo`, стирается `/start` или через 24 ч; лиды, задачи и одобрения демо само не создаёт.
В веб-чате (`POST /chat`): сообщение ровно `demo` (любой регистр) или поле `mode: "demo"` в теле возвращает короткое описание
и эту ссылку (`state: "chat"`, без песочницы).

## POST /chat (ИИ-менеджер заявок 2.0, 2026-11-22)
Заголовок `x-chat-token` (`WEB_CHAT_TOKEN`), тело JSON. Один запрос, один ответ; сессия живёт 24 часа в `web_chat_sessions` (тексты посетителя в базе не хранятся, только состояние и маска).

Запрос:
```json
{ "sessionId": "abcd-1234-...", "locale": "ru", "text": "У меня салон красоты", "page": "/ru", "ref": "dilnoza-77",
  "persona": "salon", "clientEmail": "anvar@example.com", "cabinetId": "sb-1", "clientName": "Анвар" }
```
- `sessionId`: 8..64 знаков `[A-Za-z0-9-]`. `locale`: `ru|en` (язык ответа и всех фраз кода). Слова посетителя: `text` (имя из контракта сайта) или `message` (прежнее имя), нужно одно из них, до 1000 знаков.
- `page`, `ref`: как раньше (`ref` попадает в `source: ref:<slug>` лида). `mode: "demo"` или сообщение `demo` по-прежнему возвращает описание демо-салона.
- `persona` (необязательно): `salon|clinic|shop|cafe|service|courses|personal`. `personal` (2026-11-22, вкладка «Персональный ИИ» демо сайта, `/chat?persona=personal`) это не ниша бизнеса: демо личного ИИ владельца вымышленной кофейни «Утро» (`PERSONAL_DEMO` площадки: утренняя сводка, почта, обещания, час на дела, урок английского; сценарий `demoSection.personal` сайта), без свободных окон и записи, контакты не просит, цен не называет. Включает **демо-сессию**: ИИ-менеджер заявок отвечает голосом вымышленного бизнеса этой ниши (`DEMOS` площадки агентов: название, факты, свободные окна), ответ приходит с `demo: true`. Демо ничего не пишет: ни строки сессии, ни лида, ни тикета, ни ответов владельца, контакт в демо лидом не становится; реплики живут в памяти 20 минут, не больше 12 ответов на сессию (потом короткое «это демо, число реплик ограничено»), свой лимит на IP (`perIpDemoHour`, 40 в час, сверх: 429 `rate_limited`), лог только счётчики (`persona`, число сессий). Неизвестное значение: 400 `invalid`.
- `personaKind` (необязательно, только с `persona: "personal"`, 2026-11-23): кто этот человек, `student|founder|doctor|freelancer|manager|parent|blogger|teacher|other`. Демо отвечает как помощник такого человека: в системный промпт добавляется короткий блок (кто он, 3-4 типичных дела дня, тон; RU/EN по `locale`), детали вымышленные. `other`, неизвестное значение и поле у другой `persona` игнорируются (отвечает общий личный помощник, запрос не отклоняется). Демо остаётся демо: `demo: true`, ничего не выполняется, учёт `persona:personal` и правила `DEMO_REQUIRE_CLIENT` те же.
- `clientEmail`, `cabinetId`, `clientName` (необязательно): вошедший в кабинет клиент. Он «существующий клиент»: вопросы про проект, договор, счёт, этап, статус и просьба позвать человека идут не новым лидом, а в его тред поддержки и обращением Поддержки (ответ придёт в кабинет, раздел «Сообщения», и на почту); лид из разговора привязывается к его аккаунту. Невалидное значение игнорируется.

Ответ 200:
```json
{ "ok": true, "reply": "...", "state": "chat", "buttons": [{ "id": "intake", "label": "Обсудить проект" }],
  "leadCreated": true, "ownerReplies": ["текст владельца"],
  "builderLink": "https://firtech.pro/ru/builder?b=k.salon~p.adminbot~g.booking~c.instagram",
  "cta": ["builder", "call"], "handoff": true, "demo": true }
```
- `reply`: текст для показа; в нём уже есть ссылка и предложения, поля `builderLink` и `cta` дублируют их для кнопок сайта. `state`: `chat|intake|contact|done` (`contact`: ждём контакт, `done`: лид создан).
- `builderLink`: полная ссылка на сборку с предзаполненным `?b=` (`k.<ниша сайта>`, `p.<продукт>`, `g.`, `c.`, `d.<...>.<срок>`, а у флагманов `f.<продукт>.<id-id>`; формат сайта, `firtech/src/lib/builder.ts`, порт `apps/hq/src/client/builder-link.ts`). Только когда приёмщик её предложил. `cta`: какие предложения несёт этот ответ, по порядку: `builder` (всегда первое), `call` (второе; окна из `GET <сайт>/api/slots` минус окна HQ, недоступно: «напишите удобное время»), `telegram` (только если посетитель сам просил Telegram).
- **Чанки ссылки сборки у флагманов (2026-11-22).** Продукты `personal` («Персональный ИИ») и `company` («ИИ-компания») идут в `p.` как `p.personal-company-adminbot-...` (флагманы первыми); старый `p.agent` читается как `p.personal` (в ссылках HQ его больше нет). Опции флагмана: чанк `f.<продукт>.<id-id>` после `z.` (порядок id сайта, неизвестные отбрасываются, у продукта, которого нет в `p.`, опций нет): `f.personal.` из `mail calendar tasks study notes messengers` (сервисы) и `voice memory` (возможности), `f.company.` из `sales marketing support production backoffice` (отделы) и `pult knowledge channels training` (части); пример `?b=k.coffee~p.personal-company~f.personal.mail-calendar-voice~f.company.sales-pult`. ИИ-менеджер заявок заполняет опции словами посетителя («почта, календарь, голос», «продажи и пульт») и разбирает «вся компания», «отделы», «как у вас» как `company`, «личный помощник», «для себя» как `personal`. Цены флагманов в ответе только из `GET /api/prices`: «Персональный ИИ от $290 + $29/мес», «ИИ-компания от $1 490 + $149/мес, точно по смете».
- `handoff: true`: посетитель просил живого человека или раздражён; вошедший клиент уходит в свой тред, аноним получает ссылку входа (контакт, если всё же написан, по-прежнему даёт лид), лид с пометкой «просил менеджера» появится в `/admin/chats`. `leadCreated`: создан лид; в нём `enrichment` (`docs/admin-crm-api.md`).
- `ownerReplies`: тексты, которые владелец написал этому посетителю из Пульта (выдаются один раз).
- `buttons`: только когда модель недоступна или исчерпан лимит на сессию (сценарная анкета из трёх шагов остаётся запасным путём); в обычном разговоре кнопок нет.
- Цены в ответах только из `getPrices()`: список «от $N» и правило этапов (каждый этап до начала, последний до передачи доступов, проект до `smallProjectMaxUsd` в два этапа 50 на 50, точную цену и срок называем до старта). Модель суммы не называет, предложение с чужой суммой вырезается.
- Ошибки: 400 `invalid`, 401 `unauthorized`, 413 `too_large`, 429 `rate_limited` (сессия 30 в час, IP 60 в час, демо по IP 40 в час), 503 `unavailable` (нет подключения к продажам, не касается демо). Сбой внутри обработки посетителю не показывается: уходит сценарное «принял, менеджер ответит» и запись в потерянные заявки.
- **Созвон и вход (P-03, 2026-11-22).** Посетителя, который не вошёл в кабинет, ИИ-менеджер не просит оставить контакт (сайт всё равно не примет заявку без входа): предложение созвона
  называет окна и просит «напишите номер окна (1 или 2)», а для анонима добавляет ссылку входа `<SITE_URL>/<ru|en>/cabinet/login`; просьба позвать человека тоже ведёт на вход.
  Выбор окна («1», «второе», «в пятницу в 14») сохраняется в сессии (`QState.slot`); вошедшему клиенту лид с `slot` создаётся сразу («Записал созвон: ...»), аноним после входа пишет
  «да» в той же сессии (`sessionId` тот же, теперь с `clientEmail`), и лид уходит с окном. Окна, которые HQ уже держит за другими лидами, не предлагаются.
- Состояние разговора (`QState`: ниша, боль, продукт, каналы, срок, что предложено, предложенные окна и выбранное) хранится в черновике сессии; квалификация не больше пяти реплик модели, потом предложение с тем, что известно.

## POST /audit
Бесплатный аудит сайта: результат в течение рабочего дня (не «за 24 часа»).
```
POST /audit
x-lead-token: <LEAD_WEBHOOK_TOKEN>
{ "url": "https://example.com", "contact": "@username" | "+998901234567", "name": "Дильноза", "locale": "ru" | "en", "ref": "hero" }
```
- `url`: http(s), до 200 символов, имя хоста с точкой; IP-адреса, `localhost`, `*.local` и т. п. отклоняются (400).
- `contact`: Telegram `@username` (3..32 после `@`) или телефон (7..15 цифр), 3..64 символа.
- `name` (до 80), `ref` (`[A-Za-z0-9_:.-]{1,40}`) необязательны. `locale` обязателен.
- Ответы: `200 { ok: true }`; повтор того же контакта в течение 24 ч `200 { ok: true, duplicate: true }`;
  `400 { ok:false, error:"invalid" }`; `401 unauthorized`; `413 too_large`; `429 rate_limited` (больше 20 аудитов в час на всех или больше 10 в час с одного IP посетителя;
  лимит по контакту хранится в БД, лимиты в час в памяти).
- Что происходит дальше: строка в `mk_audits` и задача Маркетинга `action: audit` «Аудит: <хост>». Голова запускает проверки SEO-исполнителя
  (title, description, h1, canonical, Open Graph, скорость ответа, viewport, кнопка Telegram/WhatsApp, форма, ссылка на Instagram),
  страницу берёт только по публичным адресам: имя хоста резолвится один раз на каждом шаге, проверяется (частные, loopback, link-local, CGNAT 100.64/10, 198.18/15, multicast, metadata, IPv6 включая 64:ff9b::/96 и IPv4 в IPv6) и соединение идёт именно на этот адрес (нет DNS rebinding); каждый редирект проверяется заново, 8 с, 1 МБ. LLM получает только факты (булевы и числа)
  и возвращает ровно 5 находок (проблема и одно исправление) и закрывающую строку с названием продукта, без цен; ответ проходит
  схему, очистку от HTML и ссылок, проверку на цены, иначе берётся шаблон. Недоступный сайт даёт находки про это и просьбу прислать
  Instagram. Результат уходит владельцу как одобрение `audit` (уровень 0, `locked`) сразу одиночной карточкой «Срочно», не в пачку 10:00; через 20 часов без отправки владельцу приходит алерт. После «Одобрить»: если контакт `@username`
  уже писал в @firtech_bot (или аудит заказан командой бота), текст отправляет клиентский бот; иначе владельцу приходит
  простой текст целиком с пометкой «отправьте вручную». Статусы `mk_audits.status`: `queued`, `proposed`, `delivered`, `handed_off`, `rejected`, `failed`.
- В боте: `/audit <сайт>` проходит тот же путь (контакт: `@username` чата, без него `tg:<chatId>`).

## GET /status
Без токена, ответ кэшируется на 60 с (`cache-control: public, max-age=60`), не больше 30 запросов в минуту с одного IP (иначе 429).
```json
{
  "ok": true,
  "generatedAt": "2026-11-19T12:00:00.000Z",
  "services": [
    { "id": "site", "title": "Website", "state": "up" },
    { "id": "omniroute", "title": "AI gateway", "state": "down", "since": "2026-11-19T11:40:00.000Z", "note": "The health check is failing" }
  ],
  "incidents": [ { "startedAt": "…", "endedAt": "…", "service": "site", "title": "Website: health check failed" } ],
  "uptime30d": { "site": 99.9, "omniroute": 100 }
}
```
- `services`: четыре записи `site`, `hq`, `bot`, `omniroute` плюс пятая `renderer` («Video renderer», `down` не бывает: при сбое `degraded`), только когда рендер рилсов включён и мониторинг его проверяет; клиент должен спокойно принимать неизвестный `id` (Polly и Dono не студийные сервисы и не показываются); `state` `up | degraded | down | unknown`;
  `since` и `note` только у `degraded` и `down` (фиксированные английские фразы). `incidents`: за 30 дней, не больше 20, новые первыми;
  без `endedAt` значит ещё идёт. `uptime30d`: только для сервисов с данными (процент 0..100, одна цифра после запятой).
- Источник: таблицы `mon_*` мониторинга (`mon_state`, `mon_samples`, `mon_incidents`). `site` = проверки хоста firtech.pro
  (health URL: `down`; сертификат: `degraded`), `omniroute` = проверка `omniroute`, `hq` = проверки `disk` и `docker` (`degraded`) и `hq` (healthcheck контейнера или файл сигнала: `down`),
  плюс сам факт ответа HQ: `up`, а если проверки не запускались больше 30 минут, `degraded`. **`bot`** (@firtech_bot): `down`, если поллинг упал или `getMe` не отвечает (две проверки подряд), `degraded`, если 10 минут нет ни сообщений, ни завершённых запросов getUpdates без ошибок поллинга (зависший поллинг); `unknown` пока бот не запущен или выключен. Нет данных мониторинга вообще: `site` и `omniroute` `unknown`.
- В ответ никогда не попадают URL, порты, токены, id проверок и тексты ошибок. Оговорка: образцы `mon_samples` хранятся 7 дней
  (`prune`), поэтому `uptime30d` считается по доступным образцам, а не за полные 30 дней; инциденты хранятся 30 дней.

## GET /blog и GET /blog/:slug
Блог сайта (2026-11-19): статья в день, HQ публикует сама после «Одобрить» в карточке «Статья дня»; сайт только читает. Без токена, ответ кэшируется на 60 с (`cache-control: public, max-age=60`),
не больше 60 запросов в минуту с одного IP (иначе 429 `rate_limited`). Каждый запрос считается по дням (`cm_kv`, ключи `blog_hits:YYYY-MM-DD`) для строки в недельном отчёте Аналитика.
```
GET /blog?lang=all
200 { "ok": true, "articles": [ Article, ... ] }      новые первыми (по `date`, затем по id), только одобренные
GET /blog/:slug
200 { "ok": true, "article": Article }
404 { "ok": false, "error": "not_found" }              нет такой статьи, не одобрена или slug не kebab-case
```
- `lang` необязателен: допустимо только `all` (обе версии RU и EN в каждой статье), другое значение даёт `400 { ok:false, error:"invalid" }`.
- `Article` ровно тип сайта (`firtech/src/content/blog/types.ts`), без лишних полей:
```json
{
  "slug": "a-booking-bot-for-your-business-where-to-start",
  "published": true,
  "date": "2026-11-19",
  "ru": { "title": "…", "description": "…", "blocks": [ … ] },
  "en": { "title": "…", "description": "…", "blocks": [ … ] }
}
```
  Блоки: `{type:"p",text}`, `{type:"h2",text}`, `{type:"list",ordered?,items:(string | {title,text})[]}`, `{type:"callout",title?,text}`, `{type:"cta",title?,text?}`.
- `date`: день одобрения (YYYY-MM-DD, часовой пояс компании `tz`). `slug`: ASCII kebab-case до 60 знаков, из английского заголовка, при совпадении с уже опубликованной добавляется `-2`, `-3`.
  Slug не меняется после публикации. Тексты прошли те же правила, что и раньше: 700-1200 слов RU, 600-1300 EN, FAQ из трёх вопросов, блок `cta`, без длинных тире, сумм в долларах и процентов.
- Статьи, ушедшие на сайт раньше через builder-issue (файлы `src/content/blog/*.ts`), в HQ не публикуются: эндпоинт отдаёт только то, что одобрено после 2026-11-19. Сайту нужно показывать оба источника.

## GET /pay/:number?k=<key>
Оплата по этапам (2026-11-21) страницу и формат ответа не меняет: каждый этап это отдельный счёт со своей ссылкой и суммой, `/pay` работает со счётом как раньше (в `title` теперь «Этап N из M: ...»).
Страница оплаты счёта на сайте: `/<locale>/pay/<number>?k=<key>` (ссылку собирает HQ: `${SITE_URL}/ru/pay/FT-2026-001?k=…`, у клиента с английским лидом `/en/`).
Сайт берёт данные здесь, передавая номер и ключ из своей ссылки как есть. Без токена: защита только в ключе (32 символа base64url, 192 бита случайности,
сравнение в постоянном времени по хэшу). Не больше 60 запросов в минуту с одного IP (как `/blog`, иначе 429 `rate_limited`). Строка счёта кэшируется на 10 с по номеру
(ключ проверяется на каждом запросе), поэтому «оплачено» появляется на странице не позже 10 с после отметки. Заголовок `cache-control: no-store` (личные данные: не кэшировать в CDN).
```
GET /pay/FT-2026-001?k=Qm9vb2tpbmctYm90LWZvci15b3VyLWJ1c2lu
200 { "ok": true, "invoice": PayInvoice }
404 { "ok": false, "error": "not_found" }     неизвестный номер, неверный или пустой ключ, черновик: ответ и работа одинаковые, существование номера не раскрывается
429 { "ok": false, "error": "rate_limited" }
```
```json
{
  "ok": true,
  "invoice": {
    "number": "FT-2026-001",
    "title": "Этап 1 из 3: «Структура и первый экран», КП #12: Сайт-визитка",
    "clientFirstName": "Dilnoza",
    "amountUsd": 150,
    "payAmountUsd": 150.07,
    "status": "issued",
    "dueDate": "2026-11-25",
    "issuedAt": "2026-11-18T04:30:00.000Z",
    "paidAt": null,
    "paidVia": null,
    "txId": null,
    "locale": "ru",
    "methods": [
      { "id": "usdt_trc20", "network": "TRON (TRC20)", "address": "T…", "note": "Только USDT в сети TRON (TRC20). Другие монеты и сети не дойдут. Переведите ровно указанную сумму: по ней платёж находится автоматически." },
      { "id": "usdt_ton", "network": "TON", "address": "UQ…", "note": "Только USDT в сети TON. Другие монеты и сети не дойдут. Переведите ровно указанную сумму: по ней платёж находится автоматически." }
    ]
  }
}
```
- Ровно эти 13 полей. `amountUsd`: сумма счёта (как в КП). **`payAmountUsd`: что перевести**, крупно и с центами («Переведите ровно 150.07 USDT»); центы добавляются,
  когда открыт другой счёт на ту же сумму (по сумме HQ находит платёж). `clientFirstName`: только первое слово имени клиента. `title`: «за что» из счёта.
- `status`: `issued` (ждёт оплаты), `paid`, `void` (отменён), `expired` (выставлен больше 45 дней назад или прошло 14 дней после `dueDate`; это только вид страницы,
  владелец всё ещё может отметить оплату вручную). Черновиков страница не видит (404).
- `methods`: только при `status: "issued"`, иначе пустой массив. Только сети, разрешённые счётом (счёт с `method=usdt_ton` покажет один TON) и заданные в `PAYMENT_DETAILS_JSON`
  (`usdt_trc20`, `usdt_ton`). `address` показывать с кнопкой копирования и QR (QR рисует сайт из `address`). `note`: на языке счёта (`locale`), RU или EN.
- `issuedAt`, `paidAt`: ISO-время или `null`. `paidVia`: `usdt_trc20 | usdt_ton | manual | null` (только у `paid`); `txId`: хэш транзакции при оплате в сети (`manual` даёт `null`):
  для TRC20 ссылка `https://tronscan.org/#/transaction/<txId>`, для TON хэш приходит в base64 (как его отдаёт toncenter): для ссылки `https://tonviewer.com/transaction/<hex>` перевести base64 в hex.
- `dueDate`: `YYYY-MM-DD`. `locale`: `ru | en`, язык лида; сайт может показывать страницу на языке из пути, тексты `note` идут на языке счёта.

### Как HQ подтверждает оплату (`billing-payment-watch`)
Каждые 2 минуты, без тихих часов (собственный cron головы Сопровождения, как мониторинг: рутина создавала бы 720 задач в день). Для каждой сети с открытыми счетами (выставлены
за последние 45 дней) один запрос: TronGrid `GET /v1/accounts/<адрес>/transactions/trc20?only_to=true&only_confirmed=true&limit=50&contract_address=TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t&min_timestamp=<ms>`
(необязательный `TRON-PRO-API-KEY: TRONGRID_API_KEY`) и toncenter `GET /api/v3/jetton/transfers?owner_address=<адрес>&jetton_address=EQCxE6mUtQJKFnGfaROTKOt1lZbDiiX1kCixRv7Nw2Id_sDs&direction=in&limit=50&start_utime=<s>`
(необязательный `X-API-Key: TONCENTER_API_KEY`). Запросы идут через `safeGetJson` ядра: только эти два хоста, https, один резолв в публичный адрес и соединение именно с ним, 8 с, 1 МБ, без редиректов.
- Перевод засчитывается, только если: контракт USDT TRC20 / мастер USDT TON совпадает, получатель наш адрес (TON сравнивается в raw-виде, user-friendly адреса декодируются
  с проверкой CRC16, без `@ton/core`), транзакция подтверждена (TON: не `aborted`), пришла не раньше выставления счёта, сумма (6 знаков, округление до центов) равна `payAmountUsd`.
  `PAY_TOLERANCE` (процент до 0.5, по умолчанию 0) разрешает недоплату в этих пределах, и то только если подходит ровно один счёт. Точное совпадение важнее; при равных суммах
  выигрывает самый старый счёт.
- Транзакция записывается в `bl_payments` (`tx_id` уникален, у счёта не больше одного платежа), счёт становится `paid` атомарно и только из `issued`, дальше те же шаги, что у `/paid`
  (старт проекта, выплата рекомендателю, онбординг), владельцу «Оплачено: … tx …». Перевод, не подошедший ни одному счёту, тоже записывается (без счёта) и даёт один алерт.
- 429/5xx и сетевые сбои: экспоненциальная пауза 2 → 4 → 8 → 16 → 30 мин; провайдер молчит больше 30 минут: один алерт, восстановление: одна строка.
- Ограничения: берутся последние 50 входящих переводов на адрес за цикл (при 2 минутах между циклами это с запасом); счета, выставленные до 2026-11-19, получили ключ задним числом,
  их сумма к переводу равна сумме счёта (центы задним числом не добавлялись).

## POST /agent/:publicId/chat (площадка агента, 2026-11-22)
Публичный чат агента клиента для его сайта и превью конструктора. Описание полей, ошибок и лимитов: `docs/admin-crm-api.md`, раздел «Кабинет v3 (2026-11-22)», §5.
- Агент клиента: `POST /agent/ag_<id>/chat`, заголовок `x-agent-token`, тело `{ text, conversationId? }`, только для `live`; токен выдаётся один раз при создании агента (`POST /admin/clients/:id/agents`). Если клиент указал `siteWidget`, запрос принимается только с этим `Origin`, CORS отвечает им же.
- Демо лида («демо на ваших данных», 2026-11-22): `POST /agent/ag_<id>/chat` с телом `{ demoKey, text, conversationId? }` без `x-agent-token` отвечает черновому агенту, которого HQ
  собрал по заявке (ключ из ссылки `<SITE_URL>/<ru|en>/demo/<publicId>?k=<ключ>` первого ответа лиду), лимит демо 50 сообщений в сутки, CORS `*`, ответ с `mode: "demo"`. Неверный
  ключ: 401. **Нужно от сайта:** страница `/<locale>/demo/<publicId>` с чатом, отправляющая `k` как `demoKey`.
- Демо для конструктора: `POST /agent/demo-<salon|clinic|shop|cafe|service|courses>/chat`, тело `{ sessionId, text }`, без токена, CORS `*`, 20 запросов в минуту и 300 в сутки с IP, память только в сессии, в базу ничего не пишется.

## Демо только для вошедших и учёт по клиенту (2026-11-23)
Владелец: «демо мог пользоваться только зарегистрированный пользователь, чтобы мы знали, кто сколько потратил». Сайт решает, кого пускать (сессия Supabase, серверно), HQ считает.
- **Кого называет запрос.** `POST /chat` (с `persona`), `POST /agent/demo-<ниша>/chat` и демо лида `POST /agent/ag_<id>/chat` с `demoKey` принимают необязательные поля: `demo: true`, `clientEmail` (регистр не важен), `cabinetId` или `clientId` (id Supabase; число, если клиент уже известен HQ как `cab_clients.id`), `clientName`. Клиент ищется по email (нет в HQ: строка `cab_clients` создаётся сразу, как при заявке из кабинета), иначе по `supabase_id` или номеру. Неизвестный id без email: запрос считается анонимным.
- **Учёт.** Таблица `demo_usage` (`client_id`, `source`, `day` в поясе компании, `calls`, `tokens_in`, `tokens_out`, `usd`): одна строка на клиента, источник (`persona:<ниша>`, `agent:demo-<ниша>`, `agent:ag_<id>`) и день. Токены и деньги берутся из usage моделей, вызванных ВНУТРИ этого сообщения (`tapLlm` в `demo-usage.ts`), цена по таблице `@fir/core`. Только числа, без текстов, имён и контактов; в лог идут `persona` и `clientId`.
- **Лимит.** `DEMO_DAILY_PER_CLIENT` (по умолчанию 30 сообщений в сутки на клиента, все источники вместе; ключ настроек `demo_daily_per_client` перекрывает env без перезапуска). Анонимные запросы под этот лимит не попадают (у них прежние лимиты на IP). Лимит агента демо лида (50 в сутки) остаётся отдельно.
- **Ответ.** В 200 и в 429 есть плоские `limit` и `remaining` и объект `usage: { limit, used, remaining }` (сайт читает любую форму), только когда запрос назвал известного клиента. Лимит исчерпан: `429 { ok: false, error: "limit_reached", limit, remaining: 0, usage }` (в `/chat` и в `/agent/*/chat` одинаково), сообщение не считается и модель не вызывается. Завтра (по поясу компании) счётчик свободен.
- **Строгий режим.** По умолчанию включён (с 2026-11-23): демо без известного клиента получает `401 { ok: false, error: "login_required" }` (`/chat`, превью и демо лида). Анонимное демо разрешает только явное `DEMO_REQUIRE_CLIENT=off`.
- **Чтение.** `GET /admin/crm/clients/:id` (клиент 360) отдаёт `demoUsage: { days: 30, messages, tokensIn, tokensOut, usd, today, bySource: [{ source, messages, usd }] }` (нули без демо; клиент без кабинета `c:<имя>` всегда с нулями). Утренняя сводка владельца: строка «Демо на сайте за сутки: N клиентов, M сообщений, $X» (только когда демо было).

## POST /lead: один канал и созвон (P-02, 2026-11-22)
`siteLeadId` (необязательно, 8..64 знаков): повтор той же заявки отвечает как первая с `duplicate: true`, лид и уведомление не создаются (72 ч, `docs/admin-crm-api.md`, «Идемпотентность заявок»).
Ответ 200 теперь `{ ok: true, id, leadId?, notified: true }`: HQ принял заявку и сам сообщит владельцу (единственный канал), бот сайта нужен только когда HQ не ответил. Поле `slot`
(ISO, окно, которое сайт уже забронировал в своей форме) становится бронью созвона в HQ (`call_bookings`, `site_state = site`): подтверждение, перенос и напоминания дальше ведёт HQ
(Пульт `POST /admin/crm/leads/:id/call`, `docs/admin-crm-api.md`, «Созвоны живут в HQ»). Брони, которые HQ ставит сам (чат, бот, Пульт), приходят на сайт `POST <SITE_URL>/api/slots`
с `x-hq-token` (контракт там же).

### Личность демо на публичном маршруте (M1, 2026-11-23)
`POST /agent/:publicId/chat` (демо-персона `demo-<ниша>` и демо лида по `demoKey`) принимает `clientEmail`/`cabinetId`/`clientId` из тела ТОЛЬКО вместе с заголовком `x-chat-token` сайта (тот же секрет, что у `POST /chat`; его шлёт серверный прокси сайта `/api/demo-agent/<id>`, не браузер). Без него тело никого не называет: запрос анонимный (по умолчанию это 401 `login_required`, пока не задано `DEMO_REQUIRE_CLIENT=off`). Демо не создаёт `cab_clients`: клиента ищут по email или `supabase_id`, неизвестный считается анонимом (кабинет создаёт клиента при входе).

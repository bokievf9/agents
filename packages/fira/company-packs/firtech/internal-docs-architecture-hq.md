# Fir Tech HQ: архитектура компании агентов (техзадание, 2026-11-19)

Решения владельца 2026-11-19: не бот на агента, а **бот на отдел** с головой-руководителем; над всеми
головами **Директор**, с которым владелец общается один; голова отдела пишет владельцу сама только
три вещи: утренняя сводка, пачка на одобрение, алерт; строим все отделы сразу, этапами; у Paperclip
берём идеи, не продукт.

## Что берём из Paperclip
Задача как единица всего (тикет с исполнителем, статусом, обсуждением, результатом, расходом);
heartbeat вместо отдельных кронов; оргчарт с подчинением и делегированием; одобрения как этапы;
бюджет и расходы по агенту, отделу, задаче; рутины создают задачи; журнал активности; экспорт
компании как шаблона.

## Слои
```
Владелец ──Telegram──▶ Директор (@firtech_hq_bot, apps/hq)
                          │ задачи, приоритеты, сводки
          ┌───────────────┼──────────────┬───────────────┬───────────────┐
      Голова            Голова         Голова          Голова          Голова
      Маркетинга        Продаж         Сопровождения   Производства    Бэк-офиса
      (бот отдела)      (бот отдела)   (бот отдела)    (бот отдела)    (бот отдела)
          │                 │              │
      Контент-мейкер    Разведчик      Мониторинг      (менеджер        (документы,
      Публикатор*       Приёмщик       Финансист        проектов)        биллинг*)
                        Пресейл*       Саппорт*
```
`*` позже. Dono и Polly остаются личными ботами (продукты), в HQ только недельные итоги.

Все отделы живут **в одном процессе** `apps/hq` на сервере (один контейнер, одна SQLite). Голова
отдела это модуль с собственным bot token (бот отдела), исполнители это модули без бота и без
крона: `run(task, ctx)`. Контент-мейкер, Разведчик, Приёмщик лидов переносятся в
`packages/workers/*` из `apps/*` с отрезанной обвязкой (бот, крон), логика и тесты сохраняются.

## Ядро `packages/hq`
SQLite (better-sqlite3), таблицы:
- `agents`: id, dept, role (director|head|worker), title, instructions (md), boss_id, status,
  trust_level, bot (имя переменной токена), budget_usd_month.
- `tasks`: id, title, body, dept, assignee_id, creator (owner|director|head|routine), parent_id,
  status (inbox|assigned|running|review|approval|done|blocked|rejected), priority, due_at,
  result (md), cost_usd, created_at, updated_at. Атомарная выдача: `claim(task, agent)` в
  транзакции с проверкой статуса.
- `task_events`: комментарии, смена статуса, результаты, ошибки (журнал задачи).
- `approvals`: привязаны к задаче; очередь из `@fir/core` переиспользуется (кнопки одобрить /
  править / отклонить, уровни доверия; деньги и цены всегда уровень 0).
- `routines`: cron, dept, assignee, шаблон задачи, политика «не запускать, пока идёт прошлая».
- `heartbeats`: очередь пробуждений (агент, причина: task|message|schedule, due_at), с
  коалесценцией; воркер ядра раз в 30 с выдаёт пробуждения по одному на агента.
- `costs`: usage по задаче и агенту из ответов OmniRoute (input/output tokens, модель, usd по
  таблице цен или 0 для бесплатных); лимиты по отделу, при превышении задача ставится в `blocked`
  и алерт владельцу.
- `activity`: кто что сделал (агент, действие, объект, время) для аудита и дашборда.
- `settings`: часовой пояс отделов, время сводки, окно тишины.

API ядра для модулей: `createTask`, `assign`, `claim`, `comment`, `complete`, `requestApproval`,
`scheduleRoutine`, `wake`, `recordCost`, `log`. Экспорт/импорт компании: `hq export` → YAML
(агенты, инструкции, рутины, без секретов), `hq import`.

## Директор `apps/hq` (бот @firtech_hq_bot)
- Только OWNER_TELEGRAM_ID. Любое сообщение владельца → LLM (strict JSON) разбирает в одно из:
  задача отделу (title, dept, priority, due), вопрос по статусу, изменение правил (пишется в
  `settings`/инструкцию агента после подтверждения кнопкой), «нужен строитель» (задача со статусом
  blocked и пометкой для главного окна Claude Code).
- Утренняя сводка 08:00 по времени владельца (Куала-Лумпур) одним сообщением: лиды и сделки, контент на сегодня и
  ждущий одобрения, инциденты, расходы за сутки, задачи blocked. Больше ничего сам не пишет.
- Пачка на одобрение: собирает `approval` всех отделов и присылает одной серией с нумерацией
  раз в день в 09:00 (время владельца) и по команде `/approve`; пакет недели приходит одной карточкой; алерты сразу, в тихие часы 23:00-08:00 копятся до сводки.
  Недельный дайджест по понедельникам 08:30 (время владельца).
- Команды: один список `apps/hq/src/commands.ts` (справка, меню до 20, обработчики): `/status`, `/tasks`, `/approve`, `/costs`, `/org`, `/level`, `/workers`, `/pause`, `/resume`, продажи, сопровождение, производство, документы, маркетинг, служебные.
- Телеграм-группа HQ (docs/hq-telegram.md): боты отделов пишут в свои темы отчёты и карточки,
  владелец только читает; Директор в теме «Общее».

## Головы отделов (модули `packages/hq/heads/*`, свой бот каждая)
Общий цикл головы на heartbeat: взять задачи отдела из `inbox`, разбить на подзадачи
исполнителям, запустить `run`, проверить результат по чек-листу отдела (LLM-ревью, strict JSON),
вернуть на доработку один раз или отправить в `approval`/`done`, написать отчёт в тему отдела.

| Отдел | Бот (env) | Исполнители на старте | Рутины |
|---|---|---|---|
| Маркетинг | `MARKETING_BOT_TOKEN` | Контент-мейкер (пакет недели: 7 рилсов, 3 поста, 2 карусели, 5 историй) | пн 06:00 пакет (час владельца); ежедневно 09:00 Душанбе «что публикуем сегодня» |
| Продажи | `SALES_BOT_TOKEN` (= @firtech_leads_bot) | Приёмщик лидов (webhook `/lead` остаётся), Разведчик (10 карточек в день) | 07:30 карточки (час владельца); дожимы 3/7 дней |
| Сопровождение | `SUPPORT_BOT_TOKEN` | Мониторинг (health firtech.pro, контейнеры, сертификат, диск, OmniRoute), Финансист (расходы OmniRoute по ключам, серверы) | каждые 5 мин проверка; 07:40 расходы в сводку (час владельца); воскресенье отчёт месяца |
| Производство | `PRODUCTION_BOT_TOKEN` | Менеджер проектов (сделка → этапы: бриф, прототип, сдача, оплата; статусы клиентам через владельца) | ежедневно 07:50 просрочки (час владельца) |
| Бэк-офис | `BACKOFFICE_BOT_TOKEN` | Документы (КП и счёт по шаблону из сделки, md/pdf) | по задаче |

Пока у отдела нет бота, его голова работает «тихо»: пишет только Директору.

## Два часа: владелец и рынок (решение владельца 2026-11-19)
Владелец живёт в Куала-Лумпуре (`OWNER_TZ`, UTC+8), рынок и клиенты в Душанбе (`TZ`, UTC+5). Обе зоны без перехода на летнее время. Настройки `owner_tz` и `tz` в БД, у рутины колонка `tz` (`company` или `owner`).

| Что | Час | Время |
|---|---|---|
| Утренняя сводка, пачка на одобрение, недельный дайджест (пн), тихие часы алертов, день режима «за столом» | владельца | 08:00, 09:00, 08:30, 23:00-08:00 |
| Всё, что должно лежать у владельца к 09:00: пакет недели (пн 06:00), тренды дня 07:30, отчёт аналитика (пн 07:00), SEO (пн 07:30), статья (вт 07:00), карточки Разведчика 07:30, дожимы 07:40, напоминания по рекомендациям 07:20, счета и напоминания 07:30, финансы 07:40, просрочки проектов 07:50, отчёты воскресенья 20:00 | владельца | см. слева |
| «Что публикуем сегодня» | рынка | 09:00 Душанбе |
| Часы клиентского бота (`CLIENT_QUIET_HOURS` 22:00-08:00), слоты звонков (`SLOT_HOURS`), демо, сроки КП и договоров, даты счетов, месяц расходов | рынка | Душанбе |
| Бэкап 03:30, очистка рендеров, мониторинг, SLA тикетов, мост к строителям, ночные рутины бэк-офиса | сервера | компании |

## Цепочка продаж: КП → договор → счёт → проект (2026-11-19)
```
лид (форма, бот, веб-чат) ─ Приёмщик: карточка, ответ ─┐
                                                      v
  есть услуга и бюджет или смета? ── да ─> Пресейл сам: КП + смета + черновик договора (presales_pack, locked)
                                   нет ─> ждёт /kp владельца
владелец утверждает КП ─> проект резервируется (pm_projects, draft, без этапов)
                         ├─> Документы: договор (bo_document, locked)
                         └─> Биллинг: счёт на 50% (billing_invoice, locked), ссылка на лид, пакет и проект
   три карточки называют друг друга: «КП #12 (утверждено) → договор → счёт 50% → проект #3 стартует после оплаты»
владелец отправляет клиенту сам, оплата криптой (USDT TRC20/TON или кошелёк из сметы)
/paid <счёт> (позже проверка в сети) ─> Производство: задача проекта, этапы по направлению КП, ТЗ на одобрение
                                    └─> лид с ref:<имя> и первый оплаченный счёт: referral_payout (10% сметы, USD, locked)
```
Остаются `locked`: счета, выплаты, документы и ответы клиентам, цены, КП, ТЗ, SEO-правки сайта. Контент (материалы и пакет недели) не `locked`: «Одобрить все обычные» его берёт,
но счётчик доверия не поднимает до уровня 1. Публикаций во внешние площадки система не делает (Instagram вручную, Telegram-канала нет).

## Заявки, которые не должны пропасть
Принятое (посетителю сказали «принято») и не дошедшее до владельца пишется как `lost_lead` (activity) и в `lost_leads` (контакт и слова), раз в час один алерт «N обращений не доставлены, причина».
Недоступный шлюз моделей: бот и веб-чат отвечают «Принял, менеджер ответит в рабочее время» и всё равно создают заявку.

## Этапы стройки (все сегодня, Sonnet)
1. **Ядро + Директор**: `packages/hq`, `apps/hq`, перенос Контент-мейкера в worker под голову
   Маркетинга (первый отдел целиком), compose-сервис `hq`, тесты, образ в CI.
2. **Продажи**: Разведчик и Приёмщик в workers под голову Продаж; `/lead` webhook внутри `apps/hq`
3. **Сопровождение**: Мониторинг и Финансист.
4. **Производство и Бэк-офис**: менеджер проектов, документы.
5. Дашборд HQ читает `activity`, `tasks`, `costs` (экспорт JSON по крону в артефакт или своя
   страница на firtech.pro/admin позже).

После этапа 1 старые сервисы `lead-intake`, `polly` остаются как есть; `content-maker`
(незапущенный) удаляется из compose; после этапа 2 удаляется `lead-intake`. Polly остаётся
отдельным сервисом.

## Мост к строителям (решение владельца 2026-11-19)
- Задача со статусом `blocked` и тегом `builder` (ставит любой агент или Директор) → Директор
  создаёт issue в `bokievf9/agents` с меткой `builder`: заголовок, отдел, контекст, ссылка на
  задачу HQ, вложения как текст (сценарий, чек-лист). Токен `GITHUB_TOKEN` fine-grained, только
  Issues read/write на один репо. Без токена задача остаётся `blocked` и попадает в сводку.
- HQ раз в 10 минут опрашивает открытые issue с меткой `builder`: закрытие issue → задача
  `review` у головы отдела с текстом последнего комментария (ссылка на результат, путь к файлу в
  `/opt/fir-agents/data/hq/artifacts/` или URL).
- Главное окно Claude Code: `gh issue list -R bokievf9/agents -l builder` при выходе на связь и по
  слову владельца; делает, кладёт результат, закрывает issue с комментарием.
- Клипы: Content Maker (бесплатная модель) пишет сценарий → одобрение владельца → Head of
  Marketing ставит `builder`-задачу «собрать клип» со сценарием → строитель пишет композицию
  Remotion, рендерит mp4 (9:16, субтитры, синтез голоса), кладёт файл → Publisher собирает пачку
  → владелец публикует и жмёт «Опубликовано».
- **Клипы с 2026-11-19 собирает сервис `renderer`, не строитель.** Одобренный рилс Head of Marketing ставит в очередь `cm_render_jobs` (общая SQLite HQ).
  Отдельный контейнер `renderer` (Node 22 + Chromium, 1,5 ГБ, без сети) раз в 20 с берёт одну задачу, озвучивает сцены Piper `ru_RU-denis-medium`,
  собирает MP4 Remotion (1080x1920, 30 к/с, субтитры по длине WAV) в `data/renders/<материал>/reel.mp4`, до 2 попыток, 10 минут на задачу.
  Publisher утром шлёт файл `sendVideo` (до 49 МБ) с кнопкой «Опубликовано»; не собралось: текст с пометкой и повтор на следующий прогон.
  `/render <id>` ставит заново, `REELS_RENDER=off` возвращает путь через `builder`. Код `packages/renderer`, очередь в `content-maker/render-queue.ts`.
- Следующий шаг: плановый облачный агент Claude Code разбирает `builder`-issue без главного окна.

## Правила
- Деньги, цены, договоры: уровень 0 всегда. Первый ответ клиенту: уровень 1.
- Исполнитель не пишет наружу сам: только через голову и одобрение.
- Все LLM-вызовы через OmniRoute (`LLM_BASE_URL`), ключ на отдел для учёта расходов (пока один).
- Секреты в `/opt/fir-agents/.env`, в коде и логах их нет.

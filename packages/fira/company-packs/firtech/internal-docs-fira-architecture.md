# Fira: одно ядро для всех агентов Fir Tech (архитектура, 2026-11-22)

Статус: **на утверждение владельца**. Код каркаса: `packages/fira` (ветка `brain-core`), к продакшену не подключён.
Основа: решения владельца 2026-11-22 и разбор `../docs/agents-expert-level-2026-11-22.md` (семь слоёв). План переноса первой
должности: `docs/fira-migration-lead-manager.md`.

Коротко. Сейчас у нас три отдельных рантайма агентов (площадка `apps/hq/src/playground.ts`, ИИ-менеджер заявок
`apps/hq/src/client/receptionist.ts`, демо-персоны `apps/hq/src/client/persona.ts`) и головы HQ со своими промптами. Fira
заменяет их одним ядром: **агент = должность × сфера × компания**, описанный данными (спецификация), один рантайм, общие
знания, память, уроки и оценка. Fir Tech = компания 0 на Fira, живой пример для клиентов. Своей LLM нет: Claude через
`@fir/core` `llm.ts` (напрямую или через OmniRoute).

---

## 1. Что такое Fira: спецификация агента (`AgentSpec`)

Код: `packages/fira/src/spec.ts`. Спецификация это данные, а не код: её можно показать владельцу, сравнить по версиям,
прогнать на eval-наборе и откатить.

| Часть | Что внутри | Где живёт |
|---|---|---|
| **Должность** (`RolePack`) | цель, обязанности, границы, когда передать человеку, метрики, стиль, инструменты по умолчанию, тир модели | `packages/fira/role-packs/<id>.md` (Markdown, правка коммитом); в базе `role_packs(id, version)` |
| **Сфера** (`NichePack`) | услуги, понятия сферы, частые вопросы, возражения, границы сферы (медицина, право, деньги), тон | `packages/fira/niche-packs/<id>.md`; `niche_packs(id, version)`; длинный материал сферы как чанки знаний (`source = niche`) |
| **Компания** (`CompanyPack`) | имя, о компании, факты, стиль (вы/ты, длина, эмодзи, языки, голос, запретные темы), права (`allow`, `deny`, `locked`), срок хранения | `companies` в Supabase; Fir Tech также `company-packs/firtech.json` |
| Знания, память, уроки компании | не в спецификации: за адаптерами (§3–5), по `company_id` | Supabase |
| **Политика модели** (`ModelPolicy`) | тир по задаче (`dialog` Sonnet, `extract`/`faq`/`judge` Haiku, `consult` Opus, `write` Sonnet), `maxTokens`, бюджет компании в месяц, `maxRounds` (4) | `agents.model` |
| **Охранники** (`GuardPolicy`) | цены, даты, штампы, длина, честная строка вместо снятого | `agents.guards` |
| **Eval-набор** | файлы `evals/*.eval.json`, которые спецификация обязана пройти до `live` | `packages/fira/evals`, результаты в `evals` |

Пакеты в Markdown: front matter (`id`, `title`, `tier`, `tools`) и разделы `## Цель`, `## Обязанности`, `## Границы`,
`## Передача человеку`, `## Метрики`, `## Стиль` (должность) или `## Услуги`, `## Термины`, `## Частые вопросы`
(`- вопрос :: ответ`), `## Возражения`, `## Границы`, `## Тон` (сфера). Разбор и проверка схемой: `packs.ts`. Первые пакеты:
`role-packs/lead-manager.md` (ИИ-менеджер заявок, собран из `apps/hq/instructions/client-bot.md`, `client/needs.ts`,
`client/receptionist.ts`) и `niche-packs/it-services.md` (сфера Fir Tech, из `needs.ts`, `client-bot.md`, `knowledge/voice.md`).

Версии. `AgentSpec.version` растёт на каждое изменение; номер версии и `fingerprint` (sha256 промпта и инструментов) пишутся
в журнал каждого хода, поэтому любой ответ привязан к точной спецификации, а сравнение «до/после» на eval честное.

Права. Инструменты агента = инструменты должности + `company.rights.allow` − `company.rights.deny` (`toolNamesOf`).
`locked` (цены, договоры, деньги) агент сам не решает: только передаёт (строка в промпте, и в HQ это виды одобрений `locked`).

## 2. Рантайм: спецификация → промпт → нативный tool use → охранники → журнал

Код: `compile.ts`, `run.ts`, `tools.ts`, `guards.ts`.

1. **Компиляция** `compile(spec, registry)` → `{ system, tools, model, missingTools, fingerprint }`. Детерминирована (без часов
   и случайностей, инструменты по имени), снимок промпта в тесте ловит любое изменение пакета. Системный промпт из двух блоков:
   - блок 1 (стабильный, `cache: true`): должность, сфера, компания, границы, когда передать, стиль, инструменты, безопасность;
     в прямом режиме Anthropic он идёт с `cache_control`, повторные ходы читают его из кэша промпта;
   - блок 2 (на каждый ход, без кэша): профиль собеседника, 3 ближайших урока, 3 ближайших куска знаний (`turnBlock`).
2. **Нативный tool use.** В `@fir/core` `LlmClient` добавлен необязательный `chat(req)` (`tools`, `tool_choice`, блоки
   `tool_use`/`tool_result`, система блоками, тир `opus`); `complete()` и `tryJson()` не менялись, старые вызовы не ломаются.
   `tryChat` никогда не бросает: `null` = откат. Через шлюз в запросе только обычные параметры Messages (система одной строкой,
   без кэша, Opus = умный алиас шлюза). `MockChatLlm` для тестов. Протокола «JSON в тексте» (как сейчас в площадке и у
   ИИ-менеджера заявок) в Fira нет.
3. **Цикл инструментов** (`run`): до `maxRounds` (4) вызовов модели; каждый `tool_use` исполняется через `runTool`
   (неизвестный или не разрешённый инструмент = `not_allowed` в `tool_result` с `is_error`, исключения внутри = `internal`),
   результат не длиннее 2000 знаков уходит обратно блоком `tool_result`. Модель, которая крутит инструменты без конца,
   упирается в потолок и уходит в откат.
4. **Инструменты.** Встроены три: `knowledge_search` (пустой результат = «не знал»), `capture_contact` (только настоящий
   контакт; в демо ничего не сохраняет), `handoff_human`. Приложение даёт свои (Fir Tech: `price_list`, `builder_link`,
   `call_slots`, сейчас заглушки в `firtech-tools.ts`). Позже: адаптер общего реестра `@fir/core` `tools` (веб, email, crm,
   календарь), права уже не по отделу (`tools/policy.ts`), а по компании (`company.rights`) поверх той же политики.
   Результат любого инструмента: `ToolResult` ядра, без исключений.
5. **Правила приложения вокруг модели**: `before` (детерминированный ответ кодом без вызова модели: просьба о человеке,
   вопрос о цене из прайса) и `after` (код дописывает свои предложения и ссылки после охранников). Так ИИ-менеджер заявок
   сохраняет принцип «модель пишет слова, код владеет состоянием, ссылками, ценами и порядком предложений».
6. **Охранники** (`applyGuards`), на каждый ответ человеку: снимаются предложения с суммой не из прайса компании (для Fir Tech
   `allowedAmounts()` сайта) и с обещанием даты или срока, вместо них одна честная строка; markdown, списки, длинные тире
   убираются; ответ режется по концу предложения; штампы и структуры `text.detect` помечаются (`flagged`), приложение
   переписывает один раз на Haiku. Границы сферы и запретные темы компании стоят в промпте, а охранники ловят то, что
   проверяется кодом. Это обобщение `client/sanitize.ts`; при переносе HQ берёт его из Fira, своя копия уходит.
7. **Откат**: модель выключена, шлюз лежит, отказ, бюджет исчерпан, пустой ответ, охранники сняли всё: лучший кусок знаний
   (оценка ≥ 0,5) или честная передача человеку. Ошибки нет никогда.
8. **Режимы хранения** (решение владельца): `live` (агент компании в работе: тексты хранятся 90 дней у компании-владельца),
   `anon` (сессия без контакта: ходы живут 24 часа для контекста, журнал без текстов; пойманный контакт продлевает разговор
   до срока `live`), `demo` (ничего не хранится). Журнал (`turns`): тир, раунды, инструменты, передача, контакт, сколько снято
   охранниками, штампы, откат, «не знал», токены; тексты только у `live` и только в `messages` с их TTL. В JSON-логи только
   id и счётчики (`fira turn`).
9. **Бюджет**: при 80% месячного бюджета агента тир опускается на ступень (Opus → Sonnet → Haiku), при 100% модель не
   вызывается (откат). Расход берётся из `costs` HQ (там уже реальная модель и токены, `meter.ts`); при переносе `meterLlm`
   получает проброс `chat`.

## 3. Знания: импорт, чанки, эмбеддинги, гибридный поиск

Код: `stores.ts` (`Knowledge`), `knowledge.ts` (`chunkText`, `wordScore`, `hybrid`, `HashEmbedder` для тестов),
`adapters/memory.ts` (`InMemoryKnowledge`), `adapters/supabase.ts` (заглушка), `sql/fira-schema.sql`
(`knowledge_chunks`, `fira_match_chunks`).

Импорт при создании агента (воркер HQ «Онбординг знаний», задача на компанию, без продакшн-данных в логах):

| Источник | Как читаем | В чанки |
|---|---|---|
| Сайт клиента | `ctx.tools.web.readable` по карте сайта, до 30 страниц, хосты из списка | текст страницы, `ref` = URL |
| Instagram | профиль и последние посты: очередь Agent Reach на Маке (`reach.instagram.*`), иначе `og` | био, подписи, закреп |
| Прайс PDF | текст PDF (нужна библиотека разбора, см. вопросы) | строки прайса, суммы в `price` |
| Прайс фото | vision: картинка в `chat` (расширение `LlmBlock` блоком `image`, следующий шаг ядра) | распознанные строки, подтверждает клиент |
| Документы | txt, md, csv, pdf из кабинета (`uploads`) | по абзацам |
| Ответы сборки | цели, услуги, часы, адрес из лида (`li_leads`, ответы сборки) | `builder` |

Чанки: `chunkText` (около 800 знаков по концам абзацев и предложений, перекрытие 100). Эмбеддинги: интерфейс `Embedder`;
в Supabase колонка `vector(1024)` с индексом HNSW. Поиск гибридный: половина слова (`ts_rank` в SQL, доля основ в памяти),
половина смысл (косинус), только внутри `company_id`, порог 0,2. Сфера: короткая выжимка в промпте, длинный материал
сферы чанками `source = niche`, ищется вместе с чанками компании.

Автогенерация FAQ. После импорта Sonnet делает черновик базы ответов: часы, адрес, цены, услуги, как записаться и 30–50
вопросов; чанки `source = faq`, `confirmed = false`. Клиент подтверждает их в кабинете одним экраном; до подтверждения
черновик не попадает в ответы (фильтр `confirmed` в `fira_match_chunks` при подключении).

«Агент не знал». Пустой `knowledge_search` или откат без знаний пишет `knowledge_misses` (вопрос, сколько раз, когда).
Раз в неделю список уходит клиенту в кабинет черновиками ответов («что спрашивали, а агент не знал»); подтверждённый ответ
становится чанком `faq`.

## 4. Память: человек, сводки, TTL

Код: `Memory` в `stores.ts`, `InMemoryMemory`. Таблицы `people`, `conversations`, `messages`.

- Ходы разговора: последние 12 в контекст (`historyTurns`), остальное не уходит в модель.
- Профиль человека по ключу контакта (телефон, Telegram id, cookie виджета, email кабинета): имя, короткие факты, сводка
  прошлых разговоров, счётчик разговоров. Склейка при `capture_contact`, записи, входе в кабинет.
- Сводка: когда разговор затих (30 минут без сообщений), Haiku пишет 2–3 строки и факты в `people.summary`/`facts`;
  в промпт идёт сводка, а не старые тексты.
- Сроки: `live` 90 дней (настройка компании `retention.liveDays`), `anon` 24 часа (`anonHours`), демо ничего. Ежечасная
  очистка (`sweep`; в Supabase pg_cron или задача HQ) удаляет истёкшее, сообщения уходят каскадом. Клиент как контролёр
  данных может удалить разговор или человека из кабинета.
- Анонимные сессии сайта Fir Tech: ходы живут 24 часа для контекста разговора и стираются; это смягчает нынешнее правило
  «тексты анонимных диалогов не хранятся» ровно настолько, насколько решил владелец.

## 5. Уроки: правка → урок → few-shot

Код: `Lessons` в `stores.ts`, `InMemoryLessons`, `lessons.ts` (`lessonFromEdit`). Таблица `lessons`.

- Источники: правка владельца в ревью-центре (`apps/hq/src/review.ts`, действие `edit`: до правки текст воркера, после
  правка владельца; `review_versions` уже хранит версии), «исправить ответ» клиента в кабинете (сообщение его агента),
  провал eval-кейса, который владелец закрыл правильным ответом.
- Урок это текст: вопрос (для HQ: суть задачи), «было», «как надо», источник, агент (или `*` для всех агентов должности в
  компании). Правка только пробелами и знаками урока не даёт.
- Применение: на каждый ход 3 ближайших урока этого агента и уроков `*` его должности, по гибридной близости к вопросу, во
  втором блоке промпта («Уроки: так компания просила отвечать на похожие вопросы»).
- Замена `decisions`. `decisions` (вид, решение, время, без текстов) остаётся для уровней доверия очереди одобрений: счётчик
  «одобрено подряд без правок» работает как сейчас. Уроки добавляют то, чего у `decisions` нет: текст правки. Правка
  владельца в ревью-центре пишет и решение, и урок; одобрение без правки урока не даёт. Тексты уроков HQ хранятся у компании
  0 (Fir Tech) и никогда не уходят в логи.
- Гигиена: не больше 200 уроков на агента, урок старше 180 дней показывается владельцу на подтверждение, противоречащие
  уроки (одинаковый вопрос, разные ответы) остаётся последний.

## 6. Оценка: набор диалогов, судья, регрессия, метрики

Код: `eval/format.ts`, `eval/runner.ts`, `eval/judge.ts`, `eval/cli.ts`; первый набор `evals/lead-manager.eval.json`
(10 кейсов из `receptionist.test.ts` и замечаний владельца).

- Формат `*.eval.json`: `name`, `spec` (компания, должность, сфера), `threshold` судьи, общие `knowledge`, `banned` (запретные
  слова для любого ответа набора), `cases[]`: `id`, `from` (откуда кейс), `lang`, `mode`, `history`, `user`, свои `knowledge`,
  `script` (ответы модели для CI) и `expect`: `contains`, `notContains`, `matches` (регулярки), `callsTool`, `notCallsTool`,
  `handoff`, `fallback`, `maxChars`, `rubric` (для судьи).
- Раннер: на каждый кейс свежие in-memory хранилища, скрипт модели или живая модель, проверки, судья. Отчёт: кейсы и метрики
  (`handoffRate`, `fallbackRate`, `unknownRate`, `toolUseRate`, `judgeMean`). Параметр `turn` подменяет рантайм: тот же набор
  гоняется на старом и на новом (сравнение при переносе).
- Судья: интерфейс `Judge`; `LlmJudge` на Haiku по рубрике (0..1, строка заметки), без модели оценка 0 и кейс падает;
  `MockJudge` в тестах.
- Регрессия в CI: `pnpm -r test` гоняет наборы в режиме скриптов (без сети и ключей: проверяются рантайм, инструменты и
  охранники). Живой прогон: `pnpm --filter fira eval evals/lead-manager.eval.json --live` (модель и судья из env); перед
  выпуском новой версии спецификации и раз в неделю, результат в `evals`. Правило выпуска: агент идёт в `live`, только если
  набор пройден целиком и `judgeMean ≥ 0,8`.
- Метрики по агенту из `turns`: доля ходов без передачи человеку, конверсия разговора в запись, лид или ссылку сборки
  (контакт, `book_slot`, `builder_link` на разговор), доля «не знал», доля откатов, снятые охранниками предложения
  (цель 0), токены и деньги на разговор. Показываются клиенту в кабинете (неделя) и владельцу в Пульте.

## 7. Данные: Supabase и что остаётся в SQLite HQ

Набросок SQL: `packages/fira/sql/fira-schema.sql` (не применён; применить к продакшн-проекту только с решения владельца).
Проект Supabase тот, что уже есть у сайта; таблицы Fira в отдельной схеме `fira`, чтобы не смешивать с таблицами сайта.

| Таблица | Ключ | Что | RLS |
|---|---|---|---|
| `companies` | `id` | компания (стиль, права, срок хранения, бюджет); `firtech` = 0 | член компании читает свою |
| `company_members` | `company_id, user_id` | кто из кабинета в какой компании | |
| `role_packs`, `niche_packs` | `id, version` | тексты пакетов | общие, только чтение |
| `agents` | `id` | должность, сфера (с версиями), политика модели, охранники, `state`, `spec_version`, наборы | своя компания |
| `knowledge_chunks` | `company_id, id` | чанк, источник, `confirmed`, `embedding vector(1024)`, `tsv` | своя компания |
| `knowledge_misses` | `company_id, query` | «агент не знал» | своя компания |
| `people` | `company_id, contact_key` | профиль, сводка, `expires_at` | своя компания |
| `conversations` | `company_id, id` | агент, канал, `mode`, контакт, `expires_at` | своя компания |
| `messages` | `company_id, conversation_id, n` | тексты ходов (`live` 90 дней, `anon` 24 часа, каскад) | своя компания |
| `lessons` | `id` | вопрос, было, как надо, источник, `embedding` | своя компания |
| `turns` | `id` | журнал хода без текстов | своя компания |
| `evals` | `id` | результаты прогонов по версии спецификации | только HQ |

Пишет только HQ сервисным ключом (обходит RLS и сам ставит `company_id` в каждой строке и фильтре); кабинет сайта читает
под пользователем, RLS пускает только к своей компании (`fira_is_member`). Хост Supabase добавляется в список хостов
`net.ts` (https, закреплённый адрес), ключ в `/opt/fir-agents/.env`.

Остаётся в SQLite HQ: очередь одобрений и `decisions`, задачи, агенты HQ и рутины, `review_versions`, лиды `li_*`, кабинет
`cab_*`, документы, счета и этапы, `costs`, `settings`, история Директора. То есть всё, что про работу самой студии и деньги.
`pg_agents`/`pg_knowledge`/`pg_messages` площадки переезжают в `agents`/`knowledge_chunks`/`messages` на шаге 3 миграции.

## 8. Каталог должностей для продажи

Каждая должность = `role-packs/<id>.md` + eval-набор; сфера и компания подставляются клиентом. Уровни продажи (решение
владельца 2026-11-22): агент → автопилот → отдел.

1. **ИИ-менеджер заявок** (`lead-manager`, готов первым). Заменяет менеджера на входящих заявках и ночные пропуски. За день:
   отвечает на заявки за секунды в Telegram, Instagram, на сайте, задаёт до трёх вопросов, предлагает сборку или созвон,
   передаёт горячих людям с контактом и сводкой. Инструменты: знания, прайс, ссылка сборки, окна созвона, контакт, передача.
2. **Администратор** (`admin`). Заменяет администратора салона, клиники, студии на записи. За день: записывает и
   переносит, напоминает накануне, собирает отзывы, отвечает про услуги и часы. Инструменты: календарь записи, знания,
   напоминания, контакт, передача.
3. **Продажник: КП и сметы** (`sales-estimator`). Заменяет менеджера, который собирает предложения. За день: по заявке и
   прайсу собирает КП и смету с точными пунктами, задаёт уточняющие вопросы, доводит до договора; цены считает код, финал
   одобряет человек (`locked`). Инструменты: прайс компании, шаблоны документов, PDF, email, CRM.
4. **Контент-менеджер** (`content-manager`). Заменяет SMM на рутине. За день: план недели, посты, карусели, сценарии
   рилсов, подписи по голосу компании; публикует после одобрения. Инструменты: плейбуки, `text.*`, картинки, очередь
   публикации.
5. **Поддержка** (`support`). Заменяет первую линию. За день: отвечает по базе знаний и статусу заказа, заводит
   обращения, передаёт сложное со сводкой, собирает «не знал». Инструменты: знания, статус заказа, тикеты, передача.
6. **Аналитик** (`analyst`). Заменяет еженедельный отчёт руками. За день: собирает цифры из таблиц, CRM и площадок,
   пишет короткий отчёт с тремя выводами и тем, что проверить. Инструменты: таблицы, CRM на чтение, события, графики.
7. **Ассистент руководителя** (`exec-assistant`). Заменяет помощника руководителя. За день: разбирает входящие,
   ставит задачи отделам, напоминает о сроках, готовит сводку утра и вечера. Инструменты: задачи, календарь, почта,
   мессенджер владельца (это и есть Директор HQ).
8. **Координатор продакшна** (`production-coordinator`). Заменяет проджекта на мелких проектах. За день: ведёт этапы,
   напоминает исполнителям и клиенту, собирает приёмку, двигает счёт следующего этапа. Инструменты: проекты и этапы,
   задачи, уведомления клиенту, счета (через одобрение).

## 9. План миграции трёх рантаймов на Fira

Общее правило: переносим по одной должности, старый путь остаётся за флагом до конца сравнения, на каждом шаге один и тот
же eval-набор гоняется на старом и новом рантайме (`runEval(..., { turn })`), выпуск только при равном или лучшем результате
и живой проверке владельца.

**Шаг 0 (эта ветка).** Ядро: `LlmClient.chat`, `packages/fira` (спецификация, компиляция, рантайм, охранники, хранилища
в памяти, заглушка Supabase, eval), первый пакет должности и сферы, первый набор. Продакшн не трогаем.

**Шаг 1. ИИ-менеджер заявок Fir Tech** (веб-чат `POST /chat` и клиентский Telegram). Подробно:
`docs/fira-migration-lead-manager.md`. Суть: `receptionistTurn` вызывает `run(spec, ...)` с `before` (просьба о человеке,
вопрос о цене, «давайте в Telegram», изменение ссылки сборки: тот же код, что сейчас) и `after` (`ctaText`: сборка, созвон,
Telegram), `QState` остаётся у приложения и обновляется из `extract`-инструмента вместо JSON. Ломается: формат ответа
модели (JSON → tool use), значит `parseModel` и тесты, проверяющие JSON-ответ мока; запросы к модели в `MockLlm` тестов
становятся `MockChatLlm`. Проверяем: 42 теста `receptionist.test.ts` (код-тесты остаются как есть), набор
`lead-manager.eval.json` на старом и новом, дрилл `apps/hq/tests/drill`, живой прогон владельца на сайте. Флаг
`FIRA_LEAD_MANAGER=on`.

**Шаг 2. Директор.** Сейчас `director.ts` разбирает сообщение владельца в один JSON (`tryJson`, Haiku, `intentSchema`:
task, status, rule, sales_reply, builder, команды голов). На Fira это должность `exec-assistant` компании `firtech` с
инструментами `create_task`, `show_status`, `propose_rule`, `sales_reply`, `create_builder`, `head_command` (обёртки над
нынешними методами `Director`), `tool_choice: any` (всегда действие или уточнение). История Директора
(`director_history`) становится памятью `live` компании 0, правки владельца в ревью-центре становятся уроками голов.
Ломается: `intentSchema` и тесты `director.test.ts`, что мокают JSON. Проверяем: набор `exec-assistant.eval.json` из
команд владельца (тексты из `director.test.ts` и дрилла), `apps/hq/tests/drill` целиком, неделя параллельного режима, где
Fira только предлагает разбор, а исполняет старый путь, и расхождения пишутся счётчиком.

**Шаг 3. Та же должность клиенту на площадке.** `pg_agents` становятся `agents` компании клиента (миграция данных с
согласия владельца: персона → `CompanyPack.about/style`, ниша сборки → `NichePack`, заметки `pg_knowledge` → чанки,
инструменты → `rights`), публичный `POST /agent/:publicId/chat` вызывает `run` в режиме `live` (виджет без контакта
`anon`), демо-персоны (`persona.ts`, `DEMOS`) становятся `demo` с пакетами сфер шести ниш. Ломается: JSON-протокол
`think()`, общий кап 300 ответов (заменяется бюджетом компании), 30 дней хранения (90/24 часа), поиск по совпадению слов
(гибридный). Проверяем: наборы по шести нишам (по 30 диалогов, §6), `apps/hq/tests/drill/cabinet-flow.test.ts`, живой агент
одного клиента в `draft` неделю, сравнение `turns` до/после.

**Дальше.** Головы HQ (маркетинг, продажи, поддержка, продакшн, бэк-офис) и воркеры с LLM переходят на `run` по одной,
каждая со своим пакетом и набором; Dono и Polly последними (у них своё ядро).

## 10. Риски и вопросы владельцу

1. **Эмбеддинги.** У Anthropic нет своего API эмбеддингов. Варианты: Voyage AI (рекомендует Anthropic, платный ключ),
   модель через шлюз OmniRoute, своя модель e5 в контейнере (память сервера 4 ГБ уже занята). Рекомендую Voyage на старте:
   нужен ключ и бюджет. Решение владельца.
2. **Tool use через бесплатных провайдеров шлюза.** Не все модели за OmniRoute умеют `tools`. Предлагаю: агенты Fira
   ходят только к моделям с tool use (Claude напрямую или проверенный маршрут шлюза), остальное через `complete`.
   Нужно согласие на расход Anthropic для live-агентов.
3. **Opus в «докторских» сферах** (клиника, право, финансы) и для пакетов знаний: включать сразу с бюджетом на компанию
   или только Sonnet на старте. Рекомендую Sonnet на старте, Opus только для написания пакетов сфер.
4. **Supabase сайта для данных агентов.** Один проект для сайта и HQ (рекомендую, схема `fira`) или отдельный проект.
   Применение схемы и сервисный ключ в `/opt/fir-agents/.env` нужны от владельца.
5. **Тексты анонимных сессий 24 часа.** Это меняет нынешнее правило сайта «тексты анонимных диалогов не хранятся»: нужна
   строка в политике конфиденциальности сайта (RU и EN).
6. **Разбор PDF и фото прайса.** Для PDF нужна новая зависимость (например `pdfjs-dist`), для фото расширение `chat`
   блоком `image` (vision). Ставлю на шаге знаний, если владелец согласен.
7. **Живой eval в CI.** Скриптовые наборы бесплатны и идут в каждом прогоне; живые стоят денег и требуют ключа в GitHub
   secrets. Рекомендую живой прогон руками перед выпуском версии и раз в неделю, а не на каждый push.
